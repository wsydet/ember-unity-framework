# 文档维护约定

维护以当前工作区为基线，区分框架公共、base、玩法模板、生成副本与历史材料。模板专属内容遵循[隔离规范](business-directory-layout.md)，模板操作说明不得依赖开发仓库的临时文件。具体审计工具和执行流程由项目的 ember-doc-maintenance Skill 提供。

1. 记录完整 Git 状态、实际 Unity/包版本、模板身份和用户范围，先保护未提交文档、内存草稿及布局。版本号、模板兼容声明和发布事实分别记录。
2. 消费项目默认只维护自有文档；本框架开发仓库可维护自有 Packages/com.ember。第三方、PackageCache、生成 bundle、模板快照和父快照只读，修改回到各自维护源并走正式流程。
3. 完整阅读范围内文档，按当前源码/API、菜单、配置所有权和生命周期判断保留、修正、合并后删除或待证据。历史测试/失败/发布记录保持日期和范围，不能把“未验证”改为通过。
4. 大改或删除前备份当前文件，不能用 HEAD 代替用户工作区。临时文件只有在独有有效契约、待办、限制和验证教训被正式承接后才能删除；文件名、时间或无入链都不是删除依据。
5. 正式契约只保留一个权威正文，其余索引引用。模板当前说明与开发仓库交付记录分开，不把完整过程日志搬到另一个巨大操作手册。
6. 修改后同步全部入链、示例和 Skill 引用；用同范围 strict 审计检查本地文件目标，再核对标题锚点和语义。机器检查通过不能证明全部文档正确。
7. 纯文档不要求运行测试；涉及脚本或资源时按 [Unity 验证](unity-validation.md)执行。工具说明需要真实窗口证据时，不能以编译或关键词检查替代。
8. 交付修改/删除理由、承接位置、实际验证与剩余事项。需要切模板由用户操作，维护动作不自动授权 Bump、提交、发布或消费升级。
