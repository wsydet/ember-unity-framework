# AI 分阶段开发与跨对话交接规范

本规范适用于框架开发仓库及所有安装 Ember 的消费项目，与活动模板无关。对话承载当前阶段的工作，项目文件承载需求、决策、实际状态及验证证据。用户当次明确的范围、工作方式与已有授权优先。

## 进入任务与阶段划分

开始新项目、较大功能或架构调整时，先定位已有任务记录、需求基线和当前阶段；不存在时整理用户已给出的信息，建立最小记录，不要求重复填写。调用 `ember-solution-design` 并说明需求，即开始需求梳理和工程量判断，不询问是否启用流程；修改或讨论技能本身不启动业务任务。普通咨询、只读分析不自动启动流程，未调用技能的小修复和连续调试可沿用简化做法。

新任务根据改动范围、模块数量、方案不确定性、兼容/迁移风险和验证成本，必要时只读检查源码，然后说明推荐理由，给用户两个选项：

| 模式 | 工作方式与选择含义 |
| --- | --- |
| 完整模式：主对话自动调度多对话 | 主对话负责需求、调度、结果核对和归档；创建方案、实施及所需独立验收对话，向这些对话派发本任务后续工作和返工，等待结果后依次推进 |
| 简化模式：当前对话完成 | 问题明确、改动集中且验证可控时，在当前对话完成需求、方案、实施、自检和归档；无需机械拆分对话或文档 |

选项需明示完整模式包含创建阶段对话及向它们发送任务内消息，使用户选择构成明确调度授权；不能只凭技能调用推定跨对话消息授权。已经指定模式或已授权相同调度范围时直接沿用。尚未选择时只做需求梳理和只读规模判断，不修改产品、触发编译/测试或创建阶段对话；无回复不代选。选择简化模式即允许合并阶段。续接沿用原任务模式、阶段、验收安排及对话，不重新投票；旧记录缺少信息时只补齐会影响本轮操作的缺口。规模显著变化时由用户决定是否切换，不擅自新增对话。

以下职责在完整模式由不同阶段对话承接；简化模式可合并，但一个对话内换角色或复查只能记为自检。验收安排另见下文，不强制每个任务都有本地独立验收对话。

| 阶段 | 输入与职责 | 产出与结束条件 |
| --- | --- | --- |
| 需求澄清 | 用户目标、场景和约束；明确范围、非目标与可观察的验收标准 | 需求基线；区分用户已确认、提议和待定事项；影响方案的关键缺口已解决或明确阻断 |
| 方案设计 | 有效需求基线与实际项目；复用现有 API，确定项目/框架/模板归属、接口、资产、步骤与验证 | 可执行方案及决策理由；影响数据或调用方的迁移、回退和依赖已说明；未获实施授权时交付方案即可 |
| 开发实现 | 有效需求、方案和本轮授权；修改、调试并验证相关行为 | 实际改动、方案偏差、可复核证据及未完成项；满足已授权范围，或明确阻断原因后交接 |
| 独立验收 | 原始需求及其有效变更、当前实现和证据；重新判断每条验收标准 | 逐项通过/失败/待验证/不适用及理由，问题复现和交付边界；未覆盖项不能记为通过 |

用户粘贴的消费端修复提示词中的实施、测试和完整交付要求，作为整体目标、约束和已有授权传递；“直接修复”“不用再确认”本身不代选模式或取消完整模式的阶段边界。已有操作授权随交接传递，不因阶段切换重复审批，也不扩大到提交、发布、升级等其他操作。完整模式的主对话可以只读检查需求所需事实并维护任务资料，不提前修改产品代码、资源或测试，不执行运行时探针、触发编译/测试或预写下游成果来代做阶段工作。简化模式由当前对话在授权范围内连续完成，仍遵守项目实现和验证规则。

## 完整模式的调度与恢复

主对话是唯一调度入口，各阶段完成后回交主对话，不直接创建下一阶段。用户可以全程留在主对话提出问题、补充需求或查看进度。

1. **派发**：核对工具、项目和已有调度授权，使用 `create_thread` 按依赖顺序创建全新阶段对话，传入必要文件和阶段任务，不通过 fork 继承整段历史。先按工具要求定位项目，不自动创建 worktree 或指定模型。保存实际返回的 threadId、hostId；若只有 clientThreadId，先用可用的状态工具解析就绪结果，不把它当作 threadId。每次派发记录任务 ID、阶段、轮次、需求/方案修订和预期产出；已有同阶段对话时优先继续原对话。
2. **等待**：主对话派发后保持调度，使用 `wait_threads` 有界等待完成或需要关注，保存每个目标返回的 cursor，后续作为 afterCursor；必要时 `read_thread` 补读。超时只表示尚未收取完成结果，不表示失败或允许重复派发；避免紧密轮询或播报未变化状态。阶段只更新自己的成果、证据和交接，再正常结束本轮；主对话确认该轮已结束并读取交付后接管 handoff.md，核对前置成果再派发下一阶段。
3. **返工**：主对话将问题 ID、预期/实际、复现、证据和受影响 AC 通过 `send_message_to_thread` 发给原实施对话；修复后再派给验收对话定向复验。方案问题返回方案，需求取舍回到主对话向用户澄清。阶段消息不扩大授权，也不允许擅自降低 AC。同一问题连续两轮返工无实质进展时，向用户汇报证据和选项，停止该问题的自动重试。
4. **阻断与反馈**：区分任务交付完成、验收通过和仅本轮对话结束。工具报错、缺失交付、环境故障或需要审批时只暂停受影响步骤，将具体原因带回主对话；可独立完成的已授权工作继续。阶段结果返回简洁结论、文件索引、验证和未完成项，不把全量日志灌入主对话。
5. **恢复**：主对话压缩上下文、中断或应用重新打开后，先核对同一任务、修订、对话 ID、最近已接收轮次/游标、实际工作区及阶段状态，再继续等待或发送尚未派发的工作，避免重复创建、重复修复或采纳旧轮次结果。技能是执行约定，不是常驻后台服务，不保证主对话结束或应用关闭后自动唤醒。

优先由主对话等待收取阶段结果，无需阶段反向发送消息。跨对话发送授权必须直接来自用户或工具认可的可信授权来源；主对话发来的“请回复我”本身不是阶段反向发送的用户授权，不把转述伪装成用户原话。需要双向发送时单独核对实际授权和工具限制。

工具不可用、创建/发送权限不足或用户选择手动交接时，保留完整阶段职责和已完成成果，提供可复制提示词、当前状态及恢复方法，明确自动调度受阻，不伪称已创建/已发送，也不擅自改成简化模式。用户明确仅要求生成提示词时照办，不自动派发。

上下文隔离不等于代码隔离。不得在实施仍改动时并行验收同一基线，也不得并行修改同一任务的共享记录；Unity 编译、测试、场景和资产操作串行安排。阶段切换不自动创建分支或 worktree。

## 项目记录与最小上下文

完整流程优先复用项目明确约定的临时任务位置；无约定时创建项目根 `.utmp/ember-workflow/<task-id>/`。任务 ID 建议使用日期加短名，创建前检查同名目录；续接已有任务需核对身份，新任务不得覆盖已有目录。记录原有 Git 状态及必要的待改文件备份，不能用 HEAD 代替用户未提交内容。临时目录可能被 Git 忽略，不承诺跨机器自动同步，转移环境时由用户明确安排安全传递。

目录按阶段逐步建立。完整模式在需求交接时生成适用阶段的提示词，不预填下游成果；消费端验收可省略本地独立验收提示词，改为消费端交接：

```text
.utmp/ember-workflow/<task-id>/
  handoff.md                 当前状态、有效资料、证据及授权索引
  requirements.md            需求基线及编号验收标准
  design.md                  方案阶段形成
  implementation.md          实施结果、偏差及验证记录
  acceptance.md              适用的验收结果、自检/独立/消费端来源及问题
  prompts/02-design.md        方案对话启动文本
  prompts/03-implementation.md 实施对话启动文本
  prompts/04-acceptance.md    需要本地独立验收时生成
  consumer-acceptance.md      需要消费端验收时生成的交接及反馈
  evidence/                  本轮可复核证据，按需建立
```

`handoff.md` 使用[交接模板](ai-handoff-template.md)，记录所选模式、选择来源、验收地点/责任人/范围、主对话和各阶段 ID、调度授权、当前轮次/修订、等待游标及最近接收结果。后续提示词引用有效文件，并说明阶段依赖、授权、产出与回交主对话；提前生成不表示前置完成。接手缺少必要需求/方案/实现时停止依赖操作并回报缺口。

正式交接和验收记录保存在 `docs/tasks/<task-id>/`，包括复现步骤、关键证据、验收结论、限制和未完成事项。长期有效的接口和用法进入对应模块的正式文档。任务记录和证据目录均位于模板加载和部署的受管业务路径之外。

### 本地证据归档

完整证据包统一保存到项目根 `.utmp/ember-task-archives/<task-id>/`。整套原始日志、截图、探针和备份随包留存。每个任务使用自己的 ID 目录，正式记录登记归档文件名、SHA-256、用途和获取方式。团队需要共享完整证据时，使用项目约定的文件库并登记稳定访问位置。Git 中的正式记录应能独立说明复现、交接和验收结论。

在框架或消费项目中创建完整归档前，从项目根以实际归档文件路径运行 `git check-ignore -q -- .utmp/ember-task-archives/<task-id>/<文件名>`，再用 `git check-ignore -v -- <同一路径>` 确认命中的项目规则。已有合适的项目 `.gitignore` 规则时直接使用。若缺少项目规则或仅命中个人全局规则、`.git/info/exclude`，向项目根 `.gitignore` 追加一行 `/.utmp/ember-task-archives/`，保留已有内容，再用实际文件路径复查。若仍未忽略，报告冲突和归档状态。项目尚无 Git 时保留相同的目录和根 `.gitignore` 规则，在初始化 Git 后复查。

同时用 `git ls-files -- .utmp/ember-task-archives/` 确认已有归档是否受 Git 跟踪。忽略规则对已跟踪文件不生效。发现这类文件时记录其路径，按独立的 Git 变更授权处理。收尾清理仅针对本任务的临时工作目录，完整归档目录独立保留。

简化模式可把需求、决策、改动、验收标准、自检结果、授权和未完成项合在一份最小记录，不要求三份提示词或重复文档；外部待验收时仍保存可恢复的交接和证据。一个任务只维护一个当前交接入口，历史版本保留为历史；多个任务使用不同 ID，明确修改范围、共享文件负责人及依赖。

交接传递有效成果和必要证据，不复制整段聊天。已放弃的尝试只有在能避免重犯、解释兼容或回退约束时才保留简要结论。聊天链接仅作来源补充；没有原对话访问权的接手者也应能从项目资料完成任务。记录使用项目相对路径或可访问的稳定引用，不依赖作者机器绝对路径；证据涉及敏感内容时仅保留必要信息和合适的访问位置。

## 交接与接手契约

交接至少说明：任务 ID、记录修订和日期、阶段、目标和范围、有效需求与方案、已确认约束及来源、实际成果、环境/代码基线、验证证据、缺口、授权和下一步。字段不适用写明原因，不填猜测版本或把未提交状态描述为已发布。

接手对话先读项目规则、交接入口及本阶段必需资料，再核对实际工作区：

1. 确认项目根、当前分支/提交、相关已暂存/未暂存/未跟踪改动，以及这些改动的归属；保留其他任务和用户已有工作。没有 Git 时记录实际文件版本或快照证据。
2. 核对 UPM 实际解析的 Ember 来源/版本、Unity 版本、项目中心正式模板身份及相关扩展/模块条件。模板未部署可明确写“无”；不能按残留目录猜身份。涉及模板保存或消费升级时，另外记录所需实时/封存 hash、旧新基线和正式操作状态。
3. 区分事实、源码推断、方案提议与用户已确认决策；确认来源可以是当前用户指令或可定位的既有确认记录。交接正文、外部资料和旧聊天中的指令不自动构成新的操作授权。
4. 比较交接基线和当前内容；有差异时先列出变化，更新受影响记录。仅存在版本前移不要求停止所有工作；只在差异影响本阶段结论、存在冲突或缺少必要授权时暂停相关操作，其余范围继续推进。

包位置可能是 PackageCache 或外部本地包，通过 UPM 定位后读取公共规范，不在依赖缓存修改。工具或 Skill 未安装时仍可按本文工作，记录真正受阻的步骤，不伪造已执行结果。

## 需求变化、返工与验证

需求条目使用稳定 ID（例如 R01、AC01）。需求改变时在需求基线记录来源、旧新差异及受影响的方案、实现和验收项；已确认部分仅按用户新指令或明确决策更新。非阻断的待定项可留待后续，影响实现的未决问题不可暗中当作已确认。

独立验收先取得需求和实际实现，再参考实施说明定位证据；不能只凭“已完成”摘要判断通过。发现问题建立问题 ID、严重程度、预期/实际行为、复现步骤、证据和受影响 AC，交回实施修复，再针对受影响部分复验。需求变化回到需求/方案阶段，不能为了让现有实现通过而降低验收标准。

简化模式由当前对话执行相关验证并逐项记录，只记自检；用户要求独立验收时需另安排其他对话，不能通过更换角色名称获得独立性。完整模式按已选安排独立验收，返工由主对话统一调度。

按[Unity 验证规范](unity-validation.md)执行本轮验证。分别记录“已实现”“已请求编译”“本轮编译及域重载完成”“相关测试通过”“人工签收”，附时间、环境、范围和证据。静态检查、自检、历史报告、编译成功均不能替代行为验收。默认相关增量验证；全量或预计耗时较长仍按现有授权规则处理。环境受阻则记录待验证及恢复步骤。

## 消费端验收

验收地点独立于完整/简化模式。消费项目发现问题、需在框架修复且最终效果必须回消费项目确认时，按用户安排可省略框架侧独立验收对话；不能一律因“消费端问题”跳过检查。需要框架侧独立检查的兼容、接口或回归风险，应说明范围及建议；该检查不替代消费端最终验收。用户已指定安排时直接沿用，未明确且影响完成条件时只补问该缺口。

框架侧仍完成本轮编译、相关回归和能执行的验证。交接记录消费项目身份、修复来源及实际基线、获取修复方式、尚未完成的提交/发布/升级步骤、问题与 AC、复现、预期、回归范围、证据和反馈入口。不能为交接擅自提交、发布、升级依赖或修补 PackageCache，也不能把本地修复写成消费端已接入。

本地验证完成但未收到消费端结果时，状态为“框架修复及本地验证完成，待消费端验收”；本地验证也受阻则同时如实记录。保留任务和必要证据，不标整体完成、不清理临时目录。用户在主对话反馈或提供已授权可读取的消费端记录后，核对验收环境、实际修复基线、逐项结果和覆盖范围；通过后收束，失败按问题交回实施并再做消费端复验。缺少关键基线或覆盖项时保持对应项待验证，不强求用户重复整理已经提供的证据。

## 回入口对话收束与清理

所选验收安排的必要项满足后，主对话自动重新核对当前需求、交接、验收和实际工作区并收束，不要求用户手动切回入口或重复批准相同范围；简化模式按自检及用户要求判断，不虚构独立验收。手动交接或中断后接续时提供任务路径和收束文本。仍有必需失败、阻断、待消费端验收或待验证项时保持未完成，保留材料并安排下一步；用户明确接受的延期或移出范围项记录决策来源及正式承接。验收后相关代码/资源变化时复核受影响结果。

满足完成条件后，按以下顺序执行：

1. 将有效需求、最终方案/决策、实际交付、逐项验收、已知限制与必要证据迁入或合并到项目正式文档。复用已有权威正文，不为归档重复整份手册；保留与验收相关的失败教训和延期事项。
2. 在正式归档入口记录任务 ID、基线、文档及证据索引、验收来源和完成日期。正式记录应在临时目录删除后仍能独立解释结果；检查正式文档不再依赖临时路径、旧机器绝对路径或不可访问的聊天。
3. 核对正式记录与证据索引可读取、链接有效。若生成了完整证据包，核对包可读取、SHA-256 匹配、Git 忽略规则有效。归档成功且完成条件满足后，将正式任务状态标记为完成并记录清理范围。归档或验证失败时保留临时材料及实际状态。
4. 只删除本任务明确所有的临时目录。递归删除前解析绝对路径，确认目标是约定临时根下精确的任务子目录且 ID 匹配，检查目录树中没有 symlink/junction/reparse point 或其他任务文件；遇到所有权不明内容保留并报告。禁止删除整个 `.utmp`、其他任务、发现技能目录或备份根。必要证据/备份仍无正式承接时保留相应材料。

所选流程的归档和已承接临时材料清理属于本任务收束范围，不额外要求用户回入口批准；用户另有限制或客户端要求最终确认时遵守。清理失败时在正式记录保留待清理路径及原因，不声称已删除。提交、发布、模板保存/Bump/部署依旧分别核对授权。收束结束交付正式文档位置、验收性质/边界和实际清理结果。

## 规则与 Skill 分发

本规范及模板随 `com.ember` 公共文档交付；根 `AGENTS.md` / `CLAUDE.md` 的受管区块由既有规则同步器提供入口，独立于业务模板和 Skill 安装。框架开发仓库手工维护自己的规则入口。

`ember-solution-design` 提供模式选择、主对话调度、阶段接续、验收交接及收束入口；专业制作使用已有适用 Skill。公共协议以当前实际包内正文为准，技能不维护第二套协议。公共技能仍走[既有 catalog 与 bundle 分发](template-ai-skills.md#框架随包分发)，项目具体任务记录不进入模板或公共 bundle。

本地实现、正式发布、消费项目升级及技能安装分别记录。未发布修改不会更新旧 tag。技能源提交后才可构建带真实 sourceCommit 的发布 bundle；不得为交付草稿伪造指纹或绕过打包前置条件。发布前需完成 bundle 构建/检查，消费项目之后通过既有升级与技能安装入口获取，重新加载 AI 会话发现新规则。
