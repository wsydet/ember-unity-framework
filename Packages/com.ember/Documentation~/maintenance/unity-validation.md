# 项目测试与 Unity 编译验证规范

本规范适用于框架开发仓库和所有安装 `com.ember` 的消费项目，与部署的模板无关。正文随框架包交付，不放入模板快照。消费项目安装或升级到包含自动同步功能的框架版本并完成 Unity 编译/域重载后，根目录 `AGENTS.md` / `CLAUDE.md` 的必读入口自动同步，区块外自定义规则保留。同步及异常处理见[包说明](../../README.md#消费项目公共规则所有模板)。包的实际位置按 UPM 解析结果确定，可能位于 `Library/PackageCache` 或外部本地目录，仅读取，不修改缓存。

## 测试范围与授权

- 需要测试时，默认仅运行本次新增的测试用例，或与本次改动直接相关的部分测试用例；执行前明确用例、测试类或过滤范围，不默认运行整个测试程序集或全量测试。
- **全量重测，或预计耗时较长的测试，必须先获得用户明确授权。** 发起前说明测试范围、必要性和预计耗时；无法可靠估算时说明不确定性，不把一般的“验证修改”视为全量或长时间测试授权。当前对话已明确授权相同范围时无需重复确认。
- 选择部分用例后仍预计耗时较长，同样需要授权；不得拆成多批绕过授权。发现需要扩大到全量或长时间测试时，先停止扩展并取得授权。
- 交付时说明实际运行范围、结果和未覆盖部分，不能把部分测试通过描述为全量通过。纯文档改动不要求运行 Unity 测试。

## 模板切换弹窗与人工确认

- 加载、切换或重新载入模板前，先告知用户目标模板以及可能出现的“模板 Skill 同步预览”、场景重载或未保存场景确认弹窗。保留正常弹窗流程，不自动绕过确认。
- 切换请求长时间未返回、超时或返回空结果时，可能是模态弹窗阻塞 Unity 主线程。应立即请用户检查并确认当前弹窗，说明正在等待哪个模板操作；不能一直等待，也不能先耗尽断连重试才提醒。
- 现有 Unity MCP 没有可靠的原生模态弹窗读取、点击接口。不要依赖另一次同通道请求关闭弹窗，不使用桌面操作代替用户确认，不把弹窗阻塞直接判定为 MCP 断连。
- 等待用户处理期间，不重复提交加载、切换、刷新或编译请求。用户回复已处理后，先查询实际模板身份、原操作结果及编辑器状态；确认切换成功后再继续必要的编译和验证。用户取消弹窗不等于切换成功，不得擅自重试或放弃未保存内容。
- 排除弹窗后仍确认为连接故障时，再执行下方有界断连恢复流程。

## Unity MCP 断连恢复

Unity 编译、域重载或其他情况可能使 MCP 暂时断连，编译结束后连接可能自动恢复。检测到无法连接、连接中断、调用超时或查询失败时，按以下流程处理：

1. 暂停依赖 MCP 的操作，**先排查是否有尚未触发编译的代码改动，不能只等待重连。** 有待编译改动且尚未提交编译请求时，先通过 Unity MCP 尝试显式请求脚本编译（例如 `refresh_unity` 的 `compile=request`）；状态查询失败不代表编译请求一定不可用。若编译请求也因断连无法送达，立即提示用户“请在 Unity 中手动触发编译，以恢复 MCP 连接”，不要等到 10 次重试耗尽才提醒。此操作用于恢复连接，仍须在恢复后通过 MCP 完成本轮编译验证。若此前编译请求已提交或超时导致结果不明，先查询状态，不盲目重复触发编译。
2. 完成上述编译触发尝试或手动编译提醒后，等待 30 秒，然后尝试重连并查询同一目标 Unity 实例的连接/编辑器状态；此后每次失败均等待 30 秒再重试。不要在每次重试时重复提交编译请求或重复提醒手动编译。
3. **最多重试 10 次**，首次检测到的失败不计入重试次数。记录次数，不紧密轮询，不在第 10 次失败后重新开始计数。
4. 任一次恢复即停止重连，检查编译或原任务状态，再继续尚未完成的验证。若待编译改动仍未触发编译，立即通过 MCP 请求编译。连接恢复本身不等于编译或测试通过；超时前已提交的刷新、测试等操作先查询状态，不盲目重复执行。
5. **10 次重试全部失败后停止依赖 MCP 的工作，请用户确认 Unity MCP 状态**；用户确认后再继续。不得无限等待或自行增加重试次数。

## 编译验证

- **代码修改完成后必须主动触发一次 Unity 重编译。** 每批 C#、程序集定义修改完成后，在运行测试、Play 验证或交付前，通过 Unity MCP 显式请求脚本编译（例如 `refresh_unity` 的 `compile=request`）；修复后同样执行。不能只等自动刷新、导入完成或用户切回编辑器。纯文档修改无需编译。
- **Unity MCP 是唯一的自动编译验证入口。** 场景或资源修改仍需通过 MCP 刷新并验证；若影响代码生成，生成完成后执行上述主动编译。
- **请求成功不等于编译完成。** 核对本轮编译和域重载已完成，确认编辑器非编译/非更新状态，并取得本轮证据（编译请求对应的完成状态/事件，或已加载新程序集、新 API/程序集 MVID 等），随后读取 Console。只有空 Console 或单次 idle 不能证明刚修改的代码已加载。仍在编译时有界等待；断线按上方 30 秒、最多 10 次规则重连，不重复提交尚未确认结果的编译/测试请求。
- 如果 Unity MCP 可用，只做一次有界的编译状态确认；仅当 MCP 明确报告正在编译时，才等待该次编译完成，禁止无意义地重复轮询。
- 如果 Unity MCP 无法连接、调用超时或查询失败，先执行上述有界重连流程；10 次重试全部失败后停止编译验证，请用户确认 MCP 状态。
- MCP 不可用时，按上方恢复流程及时提示用户手动触发编译；手动触发是连接恢复措施，不等于已完成自动编译验证。禁止通过等待 Unity 自动刷新、反复读取 `Editor.log`、轮询 Unity 进程、启动 BatchMode、临时修改生成的 `.csproj`，或运行 `dotnet build` 来替代 Unity 编译验证。
- MCP 不可用时可以继续执行即时、非阻塞的静态检查，但不得声称“编译通过”。
- **强制显式提醒：本次任务涉及需要 Unity 编译验证的改动，或正在处理 Unity 编译报错时，若重连耗尽后 MCP 仍不可用而未完成验证，最终回复必须请用户确认 MCP 状态，并明确写出“请在 Unity 中手动触发编译”。** 即使前文或上一轮已经提醒过，本轮最终回复仍不得省略；若重连恢复并实际完成验证，则按真实结果报告。
- 手动编译提醒必须同时说明“本次未完成 Unity 编译验证”，并要求用户在仍有报错时发送首条编译错误及其完整堆栈。仅写“静态检查通过”“未验证”“请刷新”或“请 Reimport”不满足要求；Refresh/Reimport 等操作建议只能作为补充，不能代替显式的手动编译提醒。

MCP 不可用时，最终回复使用以下明确表述：

> Unity MCP 按每次间隔 30 秒重试 10 次后仍未恢复，已停止依赖 MCP 的工作，请确认 MCP 状态。本次未完成 Unity 编译验证。请在 Unity 中手动触发编译；如果仍有报错，请将首条编译错误及其完整堆栈发回当前对话。
