## 3. 已有通用接口如何继续使用

| 已有接口/机制 | 可以承担 | 不承担 |
| --- | --- | --- |
| `IEmberLevelAdapter.Discover/Validate/Create/BeginTrial/StopTrial` | 项目关卡发现、诊断、创建和试玩的调用边界 | 房间/端口/能力/主题的产品模型 |
| `EmberLevelTrialSession.Start/Retry/Stop` | 正式试玩生命周期和编辑现场恢复 | 授予某项能力、读取正式游戏存档、决定邻居加载 |

| `EmberExtensionProject.Require/IsEnabled/CaptureScope/AllowsScope` | 通用扩展门禁和已打开窗口的版本身份约束 | 不把禁用 Editor 扩展解释为禁用 Player 游戏能力 |

Windward 的能力初态可先保存在自己的 `RoomTrial/Plan` 配置闭包中，通过现有关卡配置引用和冻结流程进入试玩。若现有配置依赖 hash 已覆盖全部引用，不需要再增加一套通用 payload。若项目自有数据未被冻结/指纹覆盖，先修项目捕获链；只有跨项目可复现的会话缺陷才回框架修正。

## 4. 框架待办及实施门槛

### F1：收束已经进入框架的房间图能力

当前包确实存在 `ember.level.room-graph`、`IEmberRoomGraphAdapter`、`IEmberRoomGraphTrialAdapter`、`EmberRoomGraphService`、Window/Board/Rules，以及 Windward 适配样例。这与用户最新的产品边界不符，不能再按原计划把 Windward 迁到这套框架房间图。

后续按兼容退出处理：

1. 停止为框架房间图新增能力、解锁、主题、宽口或产品进度接口。Windward 保持项目窗口，不启用此扩展作为新的依赖。
2. 先扫描所有框架/模板/消费调用方及配置，确定是否已有其他消费项目依赖；不能因为本次 Windward 尚未接入就推断没有外部调用方。
3. 在获准的后续发行中明确弃用状态与替代方向。兼容期保留已发布签名、旧配置解析、停止/清理和草稿恢复；不偷偷把旧扩展 ID 改成另一种能力。
4. Windward 不需要从框架反向复制旧样例，项目源码已经更完整。其他调用方若有需要，提供显式项目迁移说明及原资产保留策略。
5. 真正删除 API/实现要按破坏性影响选择发行边界、核对调用方并另行授权。版本号和日期待实际决定，不在此预告虚构 tag。

此次仅记录方向，**没有删除 API、改配置、关闭已打开窗口或移动文件**。不会为了修正边界而使正在进行的工作立即失效。

### F2：审计项目自有 Skill 的通用隔离支持

源码目前存在固定 `Assets/Game/Documentation/TemplateSkills` 来源、模板所有权记录、`requiredExtensions`/`requiredModuleScope`、版本/hash 校验及受管副本回收。通用扩展的自定义 SourceRoots 又限制在包内。不能直接宣称它们已经提供“独立消费项目自有 Skill 源”的全部生命周期。

Windward 的新增关卡 Skill 应属于项目，不能塞入框架公共技能 bundle，也不能为了安装它而给所有 platformer 项目分发 Windward 主题和能力。实施前先验证现有入口能否合法承载项目所有权；若不能，才在既有安装器上增量提供项目来源支持，至少保证：

- 项目自有维护源、稳定 Skill ID、声明版本与源码 hash；与模板技能源分开记录，模板升级不覆盖它。
- 依赖当前有效的 `ember.level.authoring`；试玩步骤额外要求 `ember.level.trial`；关联正式模板兼容范围和项目模块 scope。无需依赖 `ember.level.room-graph` 或蓝图。
- 预览、安装、更新、回收、修改副本备份和执行前检查复用现有事务；同名冲突报错，不接管不相关目录。
- 关闭扩展/模块、模板身份或版本/hash 失效、域重载后退出发现；旧 AI 会话再次调用仍被拒绝；源文档和制作草稿保留。
- UPM 只接收通用身份/兼容结果，不引用 Windward、Player 或项目运行类型。新 metadata 字段和接口须在实施时评审并写入正式文档，本文没有将候选路径或名称冒充现有 API。

此项是可复用的来源与隔离机制；具体 Skill 正文、需求询问、产品资产生成和玩法选择留在 Windward。项目执行前 guard 可作为开发期防误调用措施，但不能把仅有 guard、仍常驻发现的 Skill 宣称为全链路隔离完成。

### F3：通用试玩契约的定向核验

先用项目适配器验证：创建请求前拒绝无效配置；准备阶段使用冻结配置；停止/失败后恢复现场；关闭扩展后清理仍可执行；旧请求不影响新会话。只修复能够证明属于框架生命周期的问题。

不另起 Room Manager、Ability Manager、地图进度遍历器或框架解锁事件。单关真实能力断言由 Windward 的运行测试承担，框架仅用不含产品规则的测试适配器验证生命周期。

### F4：必要时单独评估模板 API

`PlayerPowerSession` 已有 CreateNewGame/Restore/Capture，`EntityPowerSnapshot` 能表达开放与资源状态；`PlayerPowerProgress` 目前是只读视图。这足以作为初态接线的基础，不证明“运行中提交一次解锁且保留资源/所有权”已经具备公开接口。

若产品既有安全接线确实不能完成运行中开放，记录最小契约缺口，再判断应留在 Windward 还是回平台模板。可复用的玩家能力提交接口属于模板业务，不能因此提升为框架必要 Manager；不能靠中途重建 Player 会话模拟解锁。模板改动须正式加载到活动 Assets 后实施和验证，再由项目中心保存；Bump/发布另行授权。其他模板不随之被迫加入能力系统。

## 5. 不安排的工作

不新增框架关卡连接/端口数据格式，不统一产品能力 ID/主题列表，不新增“通用解锁关卡”，不把 Windward 创作向导或项目 Skill 作为公共基础内容。画布排版、截图及连线现有产品实现随项目保留；未来若有独立的跨项目复用证据，可另行评估低层设施，不在本任务中借“通用画布”重新引入关卡业务。

框架关卡工作台保持与项目连接图协作：前者提供通用内容制作，后者持有关卡关系和产品侧栏。它们可以跳转同一项目场景、启动同一正式试玩会话，不要求合并窗口或替换项目资产。

### F2：确证缺口及实现

既有 schema v2 TemplateSkills 的源与 ownerKind 固定为模板；扩展 SourceRoots 又限定在包内，不能完整表达项目自有来源。新增固定项目维护源及 schema v3 catalog，复用已有预览、准备和 `EmberTemplateTransaction`；独立 ownerKind=project、projectId、声明版本、catalog/逐文件 SHA256、目录、正式模板业务基线、扩展版本/hash 和模块条件一起检查。格式、执行前 guard、备份及兼容迁移以[项目自有 Skill 正式说明](project-ai-skills.md)为准。

扩展配置变化与发现副本继续同事务提交。源/身份/模块失效和域重载检查只回收失效副本，保留项目源和修改副本备份，不自动采用新正文。清单损坏/正式身份缺失采用保守回收项目受管副本；无法安全读取所有权或备份时保留内容并报错。没有引用 Windward、Player、Entity 或新常驻 Manager/Module。

相关回归还暴露出无模块 scope 的 null 与 JsonUtility 回读空字符串被误判为更新，已按相同语义比较，避免重复同步。

### F3：正式试玩协议

保留单一 `_state` owner、跨域 SessionState、冻结请求副本与适配器职责。修复重试只检查旧配置 hash、随后接受重新发现的其他配置的问题：现在同时核对配置 GUID 和适配器 ID。待重试期间拒绝额外 Start，避免旧排队请求启动到新会话。

同步 StopTrial 抛错时取消待重试、持久化错误并退出 Play，仍允许恢复已保存的编辑现场。新增带 requestId 的 Stop/Retry/ReportFailure 重载供异步回调使用；旧签名保留，旧调用方须显式迁移到带 owner 的重载才能获得迟到回调隔离。没有虚构通用能力 payload 或项目初态机制。

配置冻结仍以已保存 Unity 资产依赖 hash 为边界；项目闭包或外部文件不自动进入冻结。进入 Play 后的产品配置副本、取消令牌、临时存储清理和真实能力断言仍由适配器承担，框架不把协议测试通过写成产品试玩验收。
