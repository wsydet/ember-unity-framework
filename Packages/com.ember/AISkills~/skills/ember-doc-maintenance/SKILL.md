# Ember 项目文档维护

以当前工作区为事实基线。用户要求维护即授权范围内的文档编辑与有依据的删除；不自动改业务代码、提交或发布。只审计时保持只读。

## 识别所有权

读取存在的 AGENTS.md、CLAUDE.md、项目文档索引与用户范围；文件不存在时不要求复制框架开发仓库文档。记录完整 git status（包括未跟踪文件）、Unity 版本、manifest/lock 与实际解析包。工作区实现、包版本、发布 tag、模板版本和部署记录分开表述。

默认采用 **consumer** 模式：项目自有 Assets/docs 可维护，所有依赖包文档只读。只有任务明确针对 Ember 框架开发仓库且实际存在自有 Packages/com.ember 源码时，才使用 **framework** 模式维护该包文档。其他自有包按用户明确范围人工核对，不把所有 embedded 包自动视为自有内容。

## 审计工具

在当前项目根运行 `python <本技能目录>/scripts/audit_docs.py --root . --mode consumer --report .utmp/ember-doc-maintenance/before.json`，框架开发任务使用 `--mode framework`。脚本随技能交付，只依赖 Python 3 和 rg 或 Git；调用时将技能目录替换成实际安装位置。

脚本优先 rg、缺失时 Git；分类和检查本地 Markdown 文件目标，不检查标题锚点、外链、API 语义或完整 Markdown 语法。自定义第三方目录可用重复的 `--exclude-dir Assets/VendorName` 排除。目录联接去重且不遍历指向项目外的文档。不自动删除或修订任何文档。

## 维护过程

1. 完整阅读范围内文档并标记保留/更新/合并后删除/待证据。对照源码的公开签名、默认值、生命周期、菜单、配置与示例；XML 注释也可能过时。
2. 优先更新现有权威文档。没有索引且用户要求完整维护时可建立项目索引；不要把框架开发目录结构强加给消费项目。
3. 大改/删除前把当前文件按相对路径备份到 `.utmp/ember-doc-maintenance/before/`，保留未提交版本；不能用 HEAD 替换用户现有内容。
4. 仅当独有设计、待办、验证教训已迁入权威文档且文件已被替代时删除。文件老、无入链或名为 TEMP 都不是独立删除依据。第三方说明、许可证、历史 CHANGELOG 和发布记录保留来源语义。
5. 更新索引与所有入链。PackageCache、外部依赖、Templates~/ParentSnapshot~ 不作为维护目标；框架升级不代表消费项目已部署的模板内容同步更新。
6. 重新运行相同模式加 `--strict`，修复本轮范围内的坏链接。无关历史问题记录而不扩张任务；检查被删除名称的残留引用与最终 diff。

纯文档/Python 改动不触发 Unity 编译。涉及 C# 或资产时按项目的 Unity 验证规则执行；不能以文档脚本通过代替 Unity 编译/运行结果。交付更新/删除范围及理由、验证结果和未确定项。已有其他技能可按需使用，未安装不阻碍本技能独立执行。
