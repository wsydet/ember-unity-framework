# Ember 方案评估

用户只要求分析时保持只读。提炼已有需求并直接调研；仅缺少会改变结论的信息时询问，不要求用户重复确认已经明确的目标。已有方案与实施授权时按授权推进，不重新设置方案门槛。

## 依据当前项目分析

读取适用的项目规则、目标脚本、相关资产和实际框架接口。消费项目的包位置可能在 Library/PackageCache 或外部本地目录，通过 manifest/lock 和实际 package.json 核对，不能假定存在物理的 Packages/com.ember。

先判断成果长期归属：产品专用玩法/资源留在项目；通用 API 或编辑器修复归框架；新项目应获得的 Assets 初始内容归模板；两者都有则联合升级。需要框架/模板改动时读取实际 Ember 包内 Documentation~/maintenance/unityfarm-change-routing.md（若存在），遵循开发仓库发布和消费端 UPM Manager 升级流程，不在 PackageCache 修补或手改模板快照。

区分已证实事实、从源码推断和未验证假设。找到现有能力时优先复用，涉及其他技能或工具时先确认可用；缺少某工具不应使纯源码分析无法进行。

## 交付可决定的方案

按问题复杂度提供有实质差异的方案，不凑数量。说明用户可见的结果、要改的模块/资产、对现有调用方和数据的影响、实现成本及回退方式。伪代码只用于解释关键契约。

给出推荐与原因，并列出最小验证：例如编译、已有行为保持、消费项目复现问题是否解决。明确哪些验证需要 Unity 环境；历史测试结果不能作为本轮证据。

停在用户要求的分析边界；需要选择且尚未授权实施时询问一次关键决策。不要把“先评估”转为自动实现，也不要在用户随后明确实施时重复确认同一方案。
