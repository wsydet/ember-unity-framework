# 大量本地修改的保护与恢复

## 1. 部署前保护

只分析时不执行部署。用户授权模板升级包含必要的保护与确定性恢复；业务互斥取舍仍需给出具体差异。完整重新部署前必须完成以下条件，不能以“之后可以恢复”代替证据。

1. 核实项目、活动模板、旧/新版本、实际部署入口和写入范围。旧原稿 O 必须与部署记录匹配，新模板 N 必须是已封存目标。补丁预览不支持跨 minor/major，不为取得预览伪造版本；通过项目中心实际全量部署入口核对条件。
2. 将 O、N、部署前 L 和部署记录、基线元数据保存为不可变快照。L 覆盖五个受管目录全部文件、目录和根目录 `.meta`，包括 Git 忽略文件、未提交文件、本地新增及二进制；不存在的路径通过完整清单表达。保存 O/N 的不存在状态才能识别本地删除。检查该版本技能同步等额外写入范围，并额外备份对应技能源、发现副本及记录；随附脚本只覆盖五目录和明确列出的证据文件，不声称覆盖所有部署副作用。
3. 默认位置为 `<项目>/.utmp/ember-template-conflict-recovery/<唯一批次>/`，必须位于实际部署和清理范围外。`.utmp` 通常被 Git 忽略且可能被清理工具删除；恢复期间保留，长周期迁移可选项目外备份。拒绝链接、junction 和嵌套在源目录中的备份目的地。先估算磁盘需求：O/N/L 快照、部署暂存、候选及部署后备份都占空间。空间不足时换位置或停止部署，不能退化为只备份冲突。
4. **复制并校验，不先搬空 Assets。** 流式处理文件并校验备份 hash；重新盘点源文件确认未变化。备份失败、权限错误、磁盘不足或发现变化时，批次不具备部署资格。停止编辑与自动生成后重新创建快照；不要把不同时间的 L 混成一个批次。部署前再验证快照和源文件。检查完成至部署之间保持编辑器和外部写入安静；这不是文件系统锁，检测到变化就重新规划。
5. 不依赖模板事务的临时 `.ember-backup~`：它在成功提交后可能被删除。旧基线会随部署推进，不能等部署后再去原位置取 O。

## 2. 随附快照工具

需要 Python 3 标准库。路径均使用真实绝对路径；以下为参数示意，不可原样执行占位路径：

```text
python <skill>/scripts/recovery_snapshot.py snapshot --project <项目根> --old-assets <可信旧原稿Assets> --new-assets <目标模板Assets> --batch <新的安全批次目录>
python <skill>/scripts/recovery_snapshot.py verify --batch <批次目录>
python <skill>/scripts/recovery_snapshot.py verify --batch <批次目录> --sources
python <skill>/scripts/recovery_snapshot.py list --batch <批次目录> --offset 0 --limit 20
python <skill>/scripts/recovery_snapshot.py list --batch <批次目录> --category review --offset 0 --limit 20
```

脚本输出摘要；完整清单保存在 `inventory.sqlite`，原始字节在 `O/`、`N/`、`L/`、`evidence/`。只有 `state.json` 为 `verified` 且最近验证成功，才可用于下一阶段。`verify` 校验副本；`--sources` 还确认源文件仍匹配，**只在部署前使用**。部署后源目录正常变化，不用它重新定义 O/N/L。脚本不判断旧模板可信度、不做模板 hash 归一化，也不处理 Unity 语义。其分类只是逐路径字节初筛，须结合公开模板算法和完整资源单元复核。不要把 `review` 数量当作真实语义冲突数。

快照中断时留下 `incomplete` 批次，不部署、不覆盖重用该批次；重新创建新批次。已验证快照上的分析与恢复可按下节清单续跑，不必重做快照。脚本没有自动恢复命令，不能把整棵 L 直接复制回 Assets。

## 3. 分类规则

以 O/N/L 路径并集盘点，文件缺失也是状态；资源、对应 `.meta`、目录 `.meta` 和路径类型一起决策。目录父子关系或 GUID 不兼容时，即使单文件字节规则可自动分类，也提升为待审单元。

| 条件 | 分类与部署后的处理 |
|---|---|
| L = N | `same`：无需恢复；包括双方一致删除 |
| L = O | `template`：采用 N；包括模板新增或删除，不能覆盖回旧文件 |
| N = O | `local`：保留 L；包括本地新增、修改、删除；恢复删除需显式删除操作，不能遗漏 |
| 其余 | `review`：比较 O→L 与 O→N，生成合并候选；同路径新增、删除/修改、路径类型变化、GUID 变化不自动拼接 |

文本差异中先排除换行和生成版本头噪声；不要重写快照。双方修改但不重叠可生成候选，仍检查调用关系与 API 兼容。跨 major/minor 时，`local` 仅表示可保留字节，不代表业务兼容；搜索旧 API、序列化、程序集和资源加载契约的受影响调用方。本地新增代码同样可能依赖被移除的 API。

冲突片段用于展示；完整 O/N/L 必须留在磁盘。二进制、场景和 Prefab 不能只保存文本差异。用户选定的业务含义、资源 GUID 和生成流程约束记入决策清单。

## 4. 持久化计划与分批执行

在批次下建立 `plan.sqlite` 或分片 JSONL 清单，不能只用聊天记忆保存进度。至少记录：

- 批次项目绝对路径、模板 ID/版本/hash、快照验证结果、阶段及实际部署回执。
- 每个资源单元稳定 ID、涉及路径、O/N/L hash/存在性、分类、拟执行的写入/删除/保留操作、候选路径与 hash、决策依据、依赖和未决原因。
- 状态 `pending / prepared / needs-decision / applying / applied / verified / failed`，写入前 C 的 hash/存在性及备份位置、预期输出 hash、实际结果和错误。

先程序生成全量路径分类与统计，再按模块和依赖排序处理；默认每批最多 20 个资源单元，巨型 YAML 或大脚本单独分块定位，但完整候选落盘。仅加载本批正文和必要调用方。每批原子更新进度，输出短摘要；未决项不阻止无依赖文件准备候选。上下文切换后先读阶段、摘要及待办分页，不重新加载全项目。

全量部署前完成恢复计划；无法确定的冲突可保留候选，但默认先解决再部署，避免项目停在不可用中间态。只有用户明确接受分阶段迁移时才带未决项进入部署。再次核验源文件、授权范围和项目中心条件；通过实际公开入口部署，工具不可用时交接已完成的备份和计划，不改业务目录模拟部署。

## 5. 部署后恢复与续跑

1. 核对实际新模板与快照 N 一致，记录部署回执和部署后状态 D。部署可能生成文件、同步技能或改写版本头，不能简单假设所有 D 都等于 N；无法解释的差异先核查，不直接覆盖。实际目标变更则重做计划。
2. 当前文件记为 C。每单元先备份 C 与 `.meta` 并写入操作意图，再检查 C 与部署后 D/上次已验证输出一致才写候选；C 已等于目标结果则跳过并核验。C 有新改动时保留它，将 D、期望恢复结果、C 作新一轮合并，不能盲目重放旧操作。
3. 本地独有内容恢复原始字节与 GUID；删除也列为操作。不得整目录覆盖 N。路径类型变化必须先解决父子操作顺序；多文件单元中断后按每文件前态/后态 hash 检查，不以部分成功标记整单元完成。候选用同目录临时文件完成后替换，失败保留快照和写前备份。
4. 续跑遇到 `applying`：当前等于预期输出则补记成功；等于写前状态则可继续；两者都不等则转待审，不能自动回滚外部新改动。回滚只涉及本批实际写入且仍等于本批输出的文件。进程退出或机器重启后同样按此规则恢复。
5. 恢复业务后再处理项目中心技能同步及 EUI 正式生成，不能用旧发现副本覆盖新维护源。整个批次结束统一做必要的 Unity 刷新和有界编译、引用/GUID 与业务验收；不用每个文件触发编译。
6. 完成条件是清单无遗漏、所有已执行操作 hash 验证通过、未决项明确、实际验证结果记录。模板版本已推进但恢复未完成时如实报告，不能宣称升级完成。备份默认保留；明确清理请求之前不删除。
