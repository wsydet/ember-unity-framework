# Ember AI 开发工作流入口

## 启动与模式选择

用户调用本技能并说明需求，即开始需求梳理和工程量判断，不再询问是否启用流程，不提供原独立方案评估模式。未提供需求时只询问要完成什么；已有信息直接整理。修改或讨论本技能本身不表示启动业务任务。

先读项目 AGENTS.md / CLAUDE.md。通过 UPM 实际解析位置定位 Ember 包，完整阅读 `Documentation~/maintenance/ai-workflow.md` 和 `ai-handoff-template.md`。包可能位于 PackageCache 或外部本地目录，不能假定存在物理的 Packages/com.ember。缺少协议文件时指出缺少的文件与影响，保留已提供的需求并说明恢复方式，不退回旧方案评估功能，不自动升级包或宣称新协议已安装。

先定位已有任务；接续时沿用其模式、阶段、验收安排及对话，不重复选择或新建任务。新任务根据范围、涉及模块、方案不确定性、兼容/迁移风险和验证成本，必要时只读检查实际源码，简要推荐并给出两个选项：

| 模式 | 适用情况与选项说明 |
| --- | --- |
| 完整模式：主对话自动调度多对话 | 跨模块、较大改动或方案/回归风险较高；主对话负责需求、调度和收束，创建方案、实施及需要的独立验收对话，并向它们派发本任务后续工作和返工 |
| 简化模式：当前对话完成 | 问题明确、改动集中且验证可控；当前对话完成需求、方案、实施、自检和收束 |

选项必须说明完整模式包含创建阶段对话及向这些对话发送任务内消息，让用户的选择成为明确调度授权；只调用技能不等于授权跨对话发送。用户已经指定模式或授权相同调度范围时直接沿用，不重复询问。尚未选择时只做需求和只读规模判断，不修改产品、触发编译/测试或创建阶段对话；无回复不代选。用户选择简化模式即允许在当前对话合并阶段。工程量变化时说明影响，由用户决定是否切换，不能擅自新增对话。

## 需求、记录与授权

提炼目标、范围、约束和可观察标准，使用稳定 R/AC ID，只询问影响结论的缺口，区分事实、推断、提议和用户决策。消费端修复提示词中的实施、回归和验证要求属于整体任务目标及已有授权，完整保留；“直接修复”“不用再确认”本身不代选模式，也不取消完整模式的阶段边界。

按公共规范判断项目/框架/模板归属并核对实际工作区，保留其他修改。完整模式沿用项目临时位置，无约定时建立 `.utmp/ember-workflow/<task-id>/`；使用公共交接模板保存需求、基线、对话身份、授权来源及归档位置。简化模式可合并为一份最小任务记录，无需三份提示词或重复文档。

## 完整模式：主对话调度

主对话保持需求、调度、结果核对和归档职责，不提前修改产品代码、资源或测试，不执行运行时探针、编译或测试来代做下游阶段。完整调度和工具降级契约以公共规范为准：

- 需求具备交接条件后，生成方案、实施和所需验收的提示词，包含实际路径、前置条件、授权、输入、产出及回交要求；不预写下游成果。消费端验收可省略本地独立验收提示词，改为消费端验收交接。
- 使用可用的 `create_thread` 按依赖顺序新建阶段对话，先核对项目；使用新上下文，不用继承全部聊天的 fork 代替隔离。记录实际返回的 threadId、hostId；未就绪的 clientThreadId 不能用于发送或等待。
- 主对话使用 `wait_threads` 等待结果，必要时 `read_thread` 补读；核对实际交付和前置条件后再派发下一阶段，不在派发后仅交付提示词并结束调度。阶段对话更新记录并正常结束本轮，不直接创建下一阶段。
- 验收失败由主对话把问题 ID、复现、证据及受影响 AC 发回原实施对话，修复后交验收对话定向复验；方案问题回方案，需求决策带回主对话。连续两轮同一问题无实质进展时回报用户决定后续，不无限循环。
- 阶段只回交简洁结论、文件索引、验证和阻断。主对话优先等待收取结果，不要求阶段反向发消息；跨对话消息不自动产生新的发送授权。

工具不可用或用户仅要求手动交接时，保留完整阶段边界，交付可直接复制的提示词和恢复方法，如实说明自动调度受阻。技能不是后台服务，不承诺主对话结束或应用关闭后必定自动唤醒；恢复时先核对记录和阶段状态，避免重复派发。

## 简化模式与阶段接续

简化模式在当前对话按有效需求和已有授权完成方案、实施、调试及相关验证，记录实际改动、偏差、逐项结果和限制。按公共 Unity 规范主动请求编译并确认本轮编译/域重载完成，默认只跑新增或相关用例；不因简化而省略必要验证。同一对话复查只记自检，不冒充独立验收。

接续已有阶段时读取有效记录并核对前置状态、授权和实际基线，完成本阶段后回交主对话，不重新选择模式或擅自接管下一阶段。方案写入 design.md；实施写入 implementation.md 和证据；独立验收直接核对需求与实际实现，写入 acceptance.md 及问题。简化任务可在同一记录中承载这些内容。

## 验收安排与收束

验收地点独立于执行模式。消费项目发现、需要框架修复且最终效果必须在消费项目确认时，可按用户安排省略框架侧独立验收对话；仍完成框架侧编译、相关回归及可执行验证。若框架风险需要额外独立检查，说明范围和建议，不能把框架检查当作消费端通过。

消费端交接写明项目和修复基线、获取修复的方式及未完成的发布/升级步骤、问题/AC、复现、预期、相关回归、证据及反馈入口。未获消费端结果时标记“框架修复及本地验证完成，待消费端验收”（本地验证未完成则如实标记），保留任务及证据；消费端反馈通过后核对其环境、修复基线和覆盖项，失败交回实施修复再复验。不擅自发布、升级或在 PackageCache 修补。

将正式交接和验收记录保存到 `docs/tasks/<task-id>/`。完整证据包统一保存到项目根 `.utmp/ember-task-archives/<task-id>/`。创建归档前按公共规范验证项目的 Git 忽略规则，缺少时补齐并复查。收尾清理只处理当前任务的临时工作目录，保留归档原件。

按所选验收安排满足必要项后，主对话自动核对当前记录与实际工作区并收束，无需用户手动切回入口或再次批准同一范围。先归档有效成果及证据、核对链接，再标完成，最后按公共规范验证绝对路径、任务 ID、所有权及无 symlink/junction 后只清理本任务临时目录。失败、受阻、待验证或验收后相关变化时保持未完成；延期/移出范围须有用户决策与正式承接。提交、发布、模板保存/Bump/部署仍分别核对授权。
