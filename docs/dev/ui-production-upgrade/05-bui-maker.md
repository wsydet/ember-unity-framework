# 阶段 S5 建立 BUI 到 Ember 的制作工具

目标是把 BUI、图片和 EUI 契约转换为可运行、可维护的正式 Prefab，并支持局部更新与结构重建。所有正式资源创建、Binding 和代码生成接入现有 EUI 开发中心。

前置为 S2 公共库、S3 Item 所有权和 S4 已确定的协议。真实导出尚未到位时可以用明确的 BUI 夹具开发解析与验证，但完整视觉和功能验收仍留给真实试点。

## 工具职责

建议形成以下服务边界，名称仅表示职责，不能当成现有 API 调用：

| 职责 | 输入与输出 | 写入范围 |
| --- | --- | --- |
| Read | BUI 和资源 → 结构化输入及协议问题 | 只读 |
| Analyze | 输入、旧契约、库配置 → 可审阅计划与差异 | 只读 |
| Preview | 计划 → 临时场景预览与诊断 | 仅临时对象，退出清理 |
| Apply | 经再次核对的计划 → 资源与 Prefab 结果 | 明确列出的目标资产 |
| Bind | 保存后 Prefab → 正式 Binding、生成代码与注册 | 现有 EUI 生成边界 |
| Verify | 当前资产 → 结构、引用、布局和行为证据 | 默认只读；修复另列 |

窗口、AI 技能和批处理共享同一套服务。分析报告不能携带隐藏写入；生成失败不能被 UI 的“完成”提示掩盖。

## 准确创建路径

1. 读取真实 BUI schema 与所有外部引用，先验证输入完整性。
2. 按 Target 依赖排序：组件和 Item 先于引用它们的页面；检测循环。
3. 通过扩展后的 EUICreationService 预检角色、输出路径、类名、骨架与资产冲突。
4. Page/Popup 以真实基础 Prefab Variant 创建；组件使用真正嵌套引用，保留连接关系。
5. 用 Unity Prefab API 构建层级、布局和控件，资源由正式导入设置配置。不写 Prefab YAML，不在运行时 Awake 拼正式 UI。
6. 调用 EUIBindingEditorUtility 等已有公开接口维护绑定；保存、重新读取实际 Prefab 后调用 TryRegenerateCode。
7. 读取实际生成结果再接入用户逻辑。自动工具不能按设计图生成未知的领奖、购买或状态切换行为。
8. 完成 Unity 编译和必要运行验证，记录真实结果。

若中心缺少需要的能力，扩展中心服务及其现有调用方，不能绕过它另造一套 Binder/页面注册。

新建与更新都遵循 S1 的 Page 命名，识别旧 Panel 仅用于迁移定位。Maker 消费当前默认皮肤或项目皮肤的明确素材与槽位，不能在生成时硬编码 macOS 风格，也不能因为新皮肤不同就重命名逻辑类。

## 节点映射与布局

| BUI 意图 | Ember 实现原则 |
| --- | --- |
| Page 或 Popup | 对应已配置骨架与明确 PageType；名称不能代替类型配置 |
| SubPage | 使用宿主矩形；按 S1 定义的 Page/Item 策略创建 |
| Group | RectTransform 布局组；装饰组不自动生成逻辑 |
| Image | 按资源语义选择 Image/必要扩展，保留九宫格和透明边缘 |
| Text | 使用项目 TMPEx/字体皮肤及文本配置；动态内容不烘焙成图片 |
| Button/Toggle/Progress | 优先匹配准确库条目和槽位，未匹配则报告候选或明确创建 |
| List | 实际 ScrollRect/容器/viewport/content 与独立 Item 模板 |
| PrefabRef | 准确源 Prefab 的嵌套实例；不能替换成空 Group |

先定义 PSD/BUI 的原点、坐标方向、单位和设计参考尺寸，再推导 RectTransform。将边界、pivot、anchors 与 PNG 像素偏移分开处理，避免“看起来差不多”的逐节点偏移补丁。

顶/中/底、安全区和弹窗内容映射到 Ember 当前真实区域。保持横竖屏配置可切换，不把试点尺寸硬编码进通用服务。旋转、缩放和裁切超出首版支持范围时明确列为限制。

## 局部更新和结构重建

| 模式 | 适用范围 | 必须保留或迁移 |
| --- | --- | --- |
| 原位更新 | 样式、资源、槽位及有限布局变化 | 资产 GUID、未触及绑定、用户代码、嵌套关系和合法覆盖 |
| 结构重建 | 页面结构/组件边界发生显著变化 | 旧功能来源、新旧接口映射、序列化与动态消费者、注册/动画引用 |

base 主界面和设置页的首次更新优先原位进行。需要变为 Variant 或大改结构时，先生成完整差异，再采用可恢复的重建路径；不能声称普通覆盖保存天然保留所有对象身份。

重建应先在候选资产验证，再在已明确范围内切换引用。动态路径、代码注册、动画路径和运行查找不一定出现在 Unity 静态依赖中，必须按 S0 行为来源补查。旧资产保留到新链路通过且消费者检查完成，再按授权清理，不能一开始删除旧 Prefab。

## 分析报告必须回答的问题

- 将创建或修改哪些资源、Prefab、Binding 和注册？准确身份是什么？
- 使用哪个骨架、哪个公共组件、哪些槽位和覆盖属性？
- 哪些绑定保留、改名、删除或变类型？是否需要用户逻辑接入？
- 哪些图片复用、导入或仅供组件内部使用？是否触及共享源？
- 哪些动态状态、隐藏页签、长文本和 Item 不能仅靠默认截图判断？
- 输入或配置变化后，哪些计划已失效？
- 操作失败时哪些资产已经保存，哪些生成/验证尚未完成？

报告与实际写入必须一致；不支持的交互和协议节点是明确问题，不能通过丢节点获得成功结果。

## 异常与重复执行

应用前备份本次受影响的资产和 .meta，记录原内容与输入版本。操作可分阶段成功，但每一步要留下实际结果；不承诺跨 Unity 崩溃的全事务回滚。

Prefab 已保存但代码生成失败时，续接生成与验证，不再次覆盖已修改美术。报告写入失败与资产制作失败分别表达。请求结果未知时先查实际产物和原请求；域重载后不自动重放写入。

再次执行相同输入，应显示无变化或明确的可应用差异，不重复建同名 Prefab、额外图集或新的用户类。用户后来修改了布局时，工具先报告差异，不无条件覆盖。

## 验收与交接

执行 M01 至 M07。必须检查共享源内容未改变、所有 PNG 引用可解析、绑定与原行为一致、重复执行不产生重复资产、非法接口变化在写入前被识别。

交付实际菜单/API、协议版本、制作计划示例、失败恢复说明、真实生成 Prefab/Binding、增量测试和 Unity 结果。将稳定能力记入包内文档，并更新 S6 可调用入口。
