# 阶段 S7 创建 UI 游戏模板并准备交付

目标是将已经通过 base 试点的 UI 能力用于正式派生模板 ui-game。模板提供通用 UI 游戏接线和中性示例，具体产品规则继续在新游戏项目实现。

本阶段与[原 UI 游戏模板方案](../color-order-ui-game/02-framework-template.md)联合执行。原方案保留生命周期与产品边界，本文件补充新的 UI 公共库、制作流程和 base 前置结果。进入时重新读取实际 API、版本和模板状态，不用旧文档数字覆盖当前工程。

## 进入条件

- S6 完整换肤试点满足范围，基础页面导航、Item 和资源生命周期通过。
- 正式 base 维护源已由项目中心普通保存，公共库和工具配置可随部署恢复。
- base 内容需要作为父模板时已完成必要封存，版本与 hash 一致。若尚未授权 Bump，先准备准确差异、验证和影响清单，不能伪造封存。
- 明确现有派生模板受影响范围，保留各模板的差异和草稿。
- 查询 ui-game 是否已存在。存在时核对是否为本任务成果，续接已有模板，不覆盖重建。

base 尚未封存时，可先使用[提示词文件](09-prompts.md)中“创建 ui-game 前的 base 父模板封存”指令完成必要本地 Bump，再执行 S7 创建。远端发布放在 ui-game 完成之后，避免把父模板封存和最终发布混成同一个阻塞步骤。

## 完成状态分开记录

| 状态 | 表示什么 |
| --- | --- |
| base 已改并验证 | 当前 Assets 可用 |
| base 已普通保存 | 模板维护内容已记录，未必封存 |
| base 已 Bump | 父模板版本与内容已正式封存 |
| ui-game 已创建和保存 | 开发端模板已形成 |
| ui-game 已 Bump | 模板内容可按该版本交付 |
| 框架已发布 | 包/tag 实际包含上述模板与工具 |
| 消费项目已验证 | 新工程实际获得并运行该交付内容 |

没有实际执行的状态保持待完成。发布前的本地交付可以完成并供审阅，不等同于已经可从远端安装。

## 创建与接线

### 1 核对 base 和派生影响

通过项目中心执行内容、资源和谱系检查。若本轮改变公共骨架 GUID、Binding 或配置模式，提供其他派生模板的迁移说明。先预览父级同步差异，再按授权处理受影响派生，不批量套用覆盖。

更改后的 base 仍能独立运行；UI 游戏示例不要进入 base 的默认启动流程。保留阶段 S0 原模板草稿，后续恢复由明确任务安排。

### 2 通过项目中心创建 ui-game

在正式“新建/派生”入口选择父模板 base，再创建并加载 ui-game。不能将当前编辑副本随意另存成名为 ui-game 的模板后假定父级正确。确认正式编辑身份、父版本和父内容基线。

创建或加载会影响受管 Assets，先保护 base 当前草稿与既有未提交内容。执行范围包含该操作时直接推进，不重复申请已明确的选择。

### 3 完成通用 UI 游戏流程

使用已有启动、Module、SceneFlow/状态和 EUI 生命周期，提供主页、局内、暂停/设置、结果和重开/返回接线。可选玩法为 Module，不新增必备 GameManager。

中性示例可以是简单的点击计数或步骤完成演示，仅用于证明一局生命周期、输入阻断、状态显示和释放。它不包含色彩排序的具体规则、关卡、得分和存档。

公共页面和控件通过 S2 骨架及 S5 制作能力获得。所有正式 UI 由中心创建和生成，新增用户逻辑保留 Runtime/Module 层级。模板调用已经明确的公共接口，不依赖 Burner 类型或工具缓存。

模板首次部署即带可用的 macOS 风格浅色默认 UI 和实际素材，页面遵守统一 Page 命名。运行示例不能只交空骨架或依赖未来美术补图；产品可沿用默认视觉，也可通过已验证的替换流程改成自己的版本。

### 4 提供美术替换示例

模板需附可实际执行的简明说明：默认皮肤和图片从哪里来、如何导出当前 EUI 契约、给美术哪些资料、如何登记自己的公共组件、如何消费 PSD/BUI、如何保持绑定，以及在哪里查看差异和结果。说明项目更换素材和样式时如何保护自己的 Assets 修改，并保留默认库的可恢复来源。

发布版文档只依赖自身、base 继承文档和实际安装包，不要求访问本机绝对路径或本目录。真实产品 PSD 和大量试点历史留在项目工作资料中，模板可附小型中性示例或明确下载/获取方式，不能引用开发机专属文件。

### 5 验证与普通保存

执行 T01 至 T05，验证正式启动、一局结束、暂停恢复、重开、返回、连续进入退出以及 Item 释放。横竖屏支持范围如实声明，至少覆盖模板选定的两种实际比例。

项目中心预览 ui-game 差异、校验并普通保存。模板说明、必要默认配置和资产都必须在受管路径内。工具只有在正确模板/模块条件下显示业务专属入口，公共 UI 工具仍可通用。

## Bump 和发布

明确授权后，通过项目中心对需要封存的 base、ui-game 执行实际 Bump，版本级别由内容和兼容性决定。不要在方案中预填未来版本或 hash。

发布使用 ember-release-framework 技能，核对包版本、模板声明、父级同步、验证、变更说明及实际 tag。提交、推送和发布按当次授权完成；只有准备动作获授权时交付可审阅清单。

模板和工具必须来自同一份兼容交付。仅更新 package.json 版本不会自动让旧消费项目获得新 Assets。

## 新消费项目接入

1. 核对实际新工程路径、Unity 版本和目标平台，读取当前包规则。
2. 通过 Ember/UPM Manager 安装或升级已交付版本，禁止手改 manifest/lock 或 PackageCache。
3. 通过项目中心预览并部署 ui-game。已有工程先保护本地内容，按正式增量或迁移策略处理，不默认完整覆盖。
4. 通过正式 AI Skill 入口安装/更新匹配版本的公共技能；确认工程路径、配置和插件能力。
5. 编译并实际运行中性示例，确认公共库引用、字体、页面注册和工具默认值有效。
6. 执行一次小范围 UI 编辑或绑定生成，验证消费端没有依赖 embedded 权限。Framework 模式页使用既有用户扩展点，新业务页/Item 使用 Business 模式。

T06 通过后，色彩顺序项目继续[产品实施阶段](../color-order-ui-game/03-consumer-project.md)，采用已确认 V2、先三个短关再扩展。基础建设不重新决定产品路线。

## 最终交接

提供实际包来源/tag/commit、base 与 ui-game 版本及内容状态、父关系、公开 API、公共库配置、插件兼容组合、技能安装入口、运行入口、已通过用例、消费验证和剩余限制。

未授权发布或尚无消费项目时，把发布准备和消费步骤准确列为待完成，保留已经完成的实现与验证；不能标记整个跨项目交付通过。
