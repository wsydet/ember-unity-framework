## 〇、决策记录（2026-08-26 用户定稿）

| 决策点 | 结论 |
|--------|------|
| 模板多版本并存 | **方案 C**：包内只发「当前 stable + 预览期 preview 模板」；历史稳定版不回包，靠旧框架 tag 获取（装旧框架 = 自带当时兼容模板） |
| 模板 × 框架兼容判定 | **major.minor 一致即兼容**（模板声明 0.8.0 → 框架 0.8.x 均显示；0.9.x 隐藏）。依据框架 SemVer：patch=小修补不应破坏模板 |
| 所有权模型 | **框架项目（dev 业务层）里出现的代码全部属于框架**；消费端用户只做补充（钩子业务、自己的页面/绑定/注册） |
| 边界标记 | **两级标记**：全文件框架 = 文件头一行；混合文件 = `[EmberManaged:begin/end]` 配对。判定标准是"这段代码谁写的"，不是"文件是什么类型" |
| 模板版本语义 | major=弃用重写（钩子删除/签名重构，用户需重写）；minor=结构变化（新钩子/新场景节点/新文件）；patch=修复（不碰用户区） |

## 一、元数据模型（template.json）

```json
{
    "id": "base",
    "displayName": "基础模板",
    "description": "...",
    "version": "0.5.0",           // 模板自身版本（独立于框架，编辑器内主/次/补丁 bump）
    "frameworkVersion": "0.10.0", // 目标框架版本：保存/新建时自动记录当前框架版本；兼容闸门判定依据
    "channel": "stable",         // stable / preview / deprecated
    "order": 1
}
```

一个模板两个版本维度：
- `version` —— 模板内容演进，独立 bump（保存内容**不覆盖**版本，仅显式 bump 时变）
- `frameworkVersion` —— 构建基准，保存/新建时自动对准当前框架；也可通过「声明为当前框架版本」单独重声明

## 二、所有权模型与两级标记语法

### 判定规则（按优先级）

| 文件 | 标记 | 升级动作 |
|------|------|---------|
| 全文件框架所有 | 文件头一行 `// Generated by Ember Setup vX.Y.Z — ...`，**无 begin/end 对** | 整体刷新（新框架版直接替换） |
| 混合文件（框架区 + 用户区） | 文件头 + `// [EmberManaged:begin X]` … `// [EmberManaged:end]` 配对 | 区块替换：begin/end 内用新框架内容替换，区外永不触碰 |
| 用户文件 | 无头标记 | 永不触碰 |

> 文件头标记所有模板 .cs 已具备，全文件框架场景零新增语法。部署时只重写头标记的版本号子串（`Generated by Ember Setup vX.Y.Z (framework vX.Y.Z)` → 真实双版本），标记本身保留。补齐缺失时对已存在文件同样刷新头行版本（只改头行、不覆盖内容，无头标记的用户文件不受影响）。

### 示例

**状态类（混合文件）：**

```csharp
// Generated by Ember Setup v0.3.0 (framework v0.9.0) — 游戏层 Main 状态（生成区文件，含业务增量）
...
public class GameMainState : MainState
{
    // [EmberManaged:begin OnMainEnter]
    protected override void OnMainEnter(object args)
    // [EmberManaged:end]
    {
        base.OnMainEnter(args);
        // ↓ 区外 = 用户区，用户业务代码
    }
}
```

**页面注册表（框架/用户拆分，partial 拼接）：**

```csharp
// GamePages.cs —— 全文件框架（头标记），框架预写页面
public static partial class GamePages
{
    public static readonly EUIPageDef MainMenu = new("...");
    // ... 框架预写的全部页面注册 ...
}

// GamePages.User.cs —— 用户文件（无标记，框架永不覆盖），codegen 默认写入此处
public static partial class GamePages
{
    // TODO: 在此处继续添加（用户页面注册区）
}
```

**EUIDefaultMainAnimation.cs（块标记）：** 只有 PlayOpeningAnimation 一个函数签名在块内（用户改函数体），其余全文件框架。

### 落地布局清单（2026-08-26 定稿并铺入模板）

- **块标记（11 个混合文件）**：① 5 个状态/动画文件——GameInitState / GameMainState / GameGameplayState / GameSettingsState 的 override 钩子签名 + EUIDefaultMainAnimation.PlayOpeningAnimation（签名框架管、函数体用户填）；② 6 个框架页面（EUIBackgroundPage/EUILoadingPage/EUIMainPage/EUIGamePlayPage/EUISettingPage/GMPage）——单个 Lifecycle 块包裹框架逻辑，块外为用户级 XxxUser 钩子（2026-08-28）
- **框架模式 codegen 页面（2026-08-27 定稿，2026-09-02 可选钩子收口）**：EUIBinding「框架」生成模式输出的页面 .cs 为混合文件——单个 `[EmberManaged:begin/end Lifecycle]` 块包裹全部生命周期 override（块内框架所有，每个 override 末尾调用对应 `XxxUser` 钩子），块外固定保留 6 个用户级钩子（OnInitUser/OnOpenUser/OnShowUser/OnHideUser/OnCloseUser/OnDisposeUser）；`OnUpdateUser` 仅随「使用 UIUpdate」生成，关闭时默认空钩子自动删除、含用户代码则确认后处理；绑定条目带 IsFramework 标记（清除/重收集受保护）；页面注册条目写入 GamePages.cs（框架区）
- **全文件框架（头标记）**：模板内其余全部框架 .cs（演示模块/UI 逻辑/BootSplash/编辑器工具等，共 52 个带标记；2026-08-27 起框架页面 EUIBackground/EUILoading 及其 Settings 也从包内迁入业务层并带头标记）
- **用户文件（无标记）**：GamePages.User.cs（用户页面注册区）+ 用户新建的状态类/模块文件（新状态=新文件，框架 FindSubclass 自动发现）
- **codegen 管理**：6 个 .Binding.cs 由 EmberCSharpImplementation 每次整文件重生成，不进两级标记体系

## 三、兼容闸门（消费端 SetupWindow）

```
可见性 = (frameworkVersion.major.minor == 当前框架.major.minor) && channel != deprecated
```

| 场景 | 行为 |
|------|------|
| 模板声明 0.8.0，框架 0.8.0 / 0.8.1 | ✅ 正常显示 |
| 模板声明 0.7.0，框架 0.8.0 | 🚫 隐藏；底部灰字「另有 N 个模板与当前框架版本不兼容」 |
| channel=preview | 显示 + 「实验性」徽标，提示谨慎使用 |
| channel=deprecated | 🚫 隐藏（等同不兼容） |

## 四、版本语义与升级提示矩阵

| 已部署 → 包内 | 判定 | 提示 | 动作 |
|---------------|------|------|------|
| 相同 | 无升级 | ✅ 已是最新 | 补齐缺失 / 重新部署 |
| patch 升级 | 绿色 | 可选升级（安全，不碰你的改动） | 一键补齐（幂等 + 标记刷新） |
| minor 升级 | 橙色 ⚠ | 结构升级（框架预写区将更新，可能影响你的联动改动） | P-B 升级向导（diff 决策）；P-A 阶段仅提示 + 补新增文件 |
| major 升级 | 红色 🚫 | 重大升级（钩子弃用，需人工迁移） | 迁移清单引导，**绝不自动删用户代码** |

## 五、部署标记与版本真实化（P-A 已实施）

- 部署时写 `Assets/Editor/EmberDeployedTemplates.json`（项目级状态，**不属于模板内容**，位于被镜像的 `Assets/Ember/Editor/` 之外，避免被 sync-scaffold 误入模板）：
  `{ templateId, version, frameworkVersion, deployedAt }`，重复部署 upsert
- 部署时重写模板文件头为双版本格式 `Generated by Ember Setup v{模板版本} (framework v{框架版本})`（保留编码与标记本身，兼容旧单版本格式）；补齐缺失时对已存在文件同样刷新头行版本（只改头行、不覆盖内容，无头标记的用户文件不受影响）
- 标记丢失 → 视为首次部署，走补齐模式（不覆盖）

## 六、升级向导（P-B 设计定稿，未实施）

按 §二 所有权判定对文件三分类处置：

| 类别 | 升级动作 |
|------|---------|
| 全文件框架 | 整体刷新（直接替换） |
| 混合文件 | 区块合并：匹配 `[EmberManaged:begin X/end]` 对 → 区块内替换；缺配对 → 在安全位置插入新区块（类尾/文件尾）；签名冲突 → ⚠ 报警跳过 |
| 用户文件 / 新增文件 | 永不触碰 / 直接补 |
| codegen 管理文件（.Binding.cs） | 升级不碰；由 EmberCSharpImplementation 每次整文件重生成 |
| 场景 | 补全模式（只增缺失节点，沿用 FrameworkSceneBootstrapper 增量思路） |
| 钩子弃用 | 基类加 `[Obsolete("请改用 Xxx（vX.Y.Z）")]` → 编译警告自然到达 + 向导迁移清单；框架永不删用户函数 |
| 用户删了标记 | 该文件降级为纯 diff 人工合并（保守兜底） |

所有操作 **dry-run 先展示差异清单，确认后才写**；合并器只做行级定位，签名不匹配即跳过，永不半写。

## 九、风险兜底

| 风险 | 兜底 |
|------|------|
| 用户删标记（头标记或 begin/end） | 文件降级：无头标记 → 永不触碰；缺配对 → 纯 diff 人工合并 |
| 标记解析脆弱（嵌套/多行） | 合并器只做行级定位，签名不匹配即跳过，永不半写 |
| 部署记录被删 | 视为首次部署，补齐模式 |
| patch 框架升级后模板闸门 | major.minor 判定 → 0.8.1 自动兼容 0.8.0 声明，无感 |
| 未来模板增多 | channel/frameworkVersion 机制天然支持，无需改窗口 |
| 用户在框架区内改代码 | 违反"用户只补充"约定 → 升级会被覆盖（文档明确约定，向导 diff 展示让用户知情） |
