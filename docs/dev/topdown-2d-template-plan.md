# topdown-2d 模板实施方案

日期：2026年10月28日  
状态：实施方案，尚未开始模板实现  
配套方案：[永夜项目实施方案](evernight-project-plan.md)

在 Ember 中新增直接继承 `base` 的 `topdown-2d` 模板，交付一个可以正式启动、操作、战斗、保存和恢复的二维俯视玩法起点。模板提供通用角色与关卡接线，具体游戏在部署后的 Assets 中开发自己的规则。

本次已确定继承关系与产品分工。下文的首版范围、默认策略和阶段划分是建议实施基线；不表示已创建模板、完成验收或取得保存、Bump、发布授权。正式模板文档应在实现后维护于 `Assets/Game/Documentation/topdown-2d/`，本文件保留为开发仓库中的设计与实施依据。

## 1 目标与范围

```text
Ember 框架公共能力
└── base
    ├── platformer-2d
    ├── topdown-2d
    ├── visual-novel
    └── 其他派生模板

永夜项目 → 部署 topdown-2d → 添加产品玩法与内容
```

`topdown-2d` 与 `platformer-2d` 平级，不继承平台跳跃的地面、空中、跳跃、墙面和承载规则。首版应交付下列可见结果：

- 经 Framework → Main → Gameplay 正式流程进入俯视白盒。
- 角色能够平面移动、转向、碰撞，执行一次近战与一种冲刺或闪避示例。
- 攻击目标、受击、击退、无敌、死亡和恢复形成完整链路。
- 可以暂停、保存退出、继续游戏，并能创建第二个关卡重复使用同一玩家配置。
- 项目能新增动作、替换输入或表现、接入世界进度，而无需改写模板运行主循环。

首版不包含产品剧情、提灯、污染、茧、命途、装备构筑、背包经济、随机地牢、通用任务系统、联网、多玩家、复杂寻路、3D 高度层或完整弹幕系统。简单敌人属于验证样例，不作为完整 AI 产品承诺。

### 1.1 建议采用的技术边界

| 项目 | 首版范围 |
| --- | --- |
| 空间与物理 | XY 平面、Physics2D、零重力；Z 和渲染排序不承载独立玩法高度 |
| 视角 | 正交俯视相机；正式美术可采用有纵深感的二维素材，但不引入 3D 运动 |
| 控制对象 | 单个玩家；移动与瞄准方向分离，保留只跟随移动朝向的配置方式 |
| 输入 | 键鼠完成基线；预留并接线手柄摇杆与按钮，真实设备验收单列 |
| 战斗 | 可选装配；启用后提供完整最小示例，关闭后仍可移动和进入关卡 |
| 动画 | 逻辑方向使用连续向量；四向、八向和左右翻转属于表现映射，不限制运动方向 |
| 首轮环境 | 当前 Unity 工程和 Windows 开发环境；产品发行平台另行确定 |

## 2 当前基线与复用分类

2026年10月28日核对的本地包版本为 `com.ember 0.24.3`；正式编辑记录为 `platformer-2d 0.13.0`。模板 metadata 中 `base` 为 `0.10.0`，`platformer-2d` 为 `0.13.0`、父版本为 `base 0.10.0`。这些是此次规划的读取基线，不证明工作区所有改动已发布。实施 T0 时重新核对实际版本、内容 hash 和未保存差异。[S1]

“直接复用”表示沿用现有公共接口或父模板内容，仍需完成新模板接线；“适配复用”表示已有实现提供可靠起点，但不具备直接安装即用的俯视语义。

| 能力 | 已有依据 | 处理方式 | 首版需要完成的工作 |
| --- | --- | --- | --- |
| 生命周期与模块装配 | Ember Managers、Modules、Init/Main/Gameplay | 直接复用 | 新业务显式声明 Phase 与 Enabled；不新增全局 PlayerManager |
| 场景准备、转场与输入开放 | base SceneFlow、GameSceneScope、请求准备与提交链 | 直接复用 | 新增俯视玩家准备参与者；输入在完整可交互阶段开放 |
| 输入服务 | EmberInputManager、base GameInputModule | 直接复用 | 配置移动、瞄准、攻击、冲刺、交互；处理新按下与恢复语义 |
| 资源、音频、相机设施 | Ember Resource、Audio、Camera | 直接复用 | 玩家相机适配、资源装配和声音调用由模板负责 |
| UI、配置表与本地化 | EUI、Table、base 公共页面 | 直接复用 | 增加必要状态显示与恢复交互；正式 UI 由 EUI 中心制作 |
| 存储后端与槽位 | base PlayerDataModule | 直接复用 | 启用模块，定义俯视完整进度类型、codec 和恢复流程 |
| 层级 FSM 与观察 | EmberFsm、图、参数与观察登记 | 直接复用 | 新建俯视 Context、状态、图和所属模板的蓝图登记 |
| 方案配置、捕获与复制 | 平台 PlayerScheme、Capture、配置校验工作流 | 适配复用 | 建立俯视配置闭包；保留源配置与本次运行配置的区别 |
| 能力次数、冷却、效果、生命 | 平台 Entity Powers、Effects、EntityHealth | 适配复用 | 核对并移植必要闭包；验证宿主隔离、暂停、清理与保存语义 |
| 运动与朝向 | EntityMotor2D、EntityFacing2D、PlayerController | 部分算法复用，新增俯视接线 | 向量运动、瞄准、加减速、碰撞、冲刺和朝向所有权 |
| 攻击、命中与击退 | 平台攻击窗口、PlayerHitQuery、EntityHit | 适配复用 | 从左右镜像改为方向旋转；统一命中坐标、击退向量和预览 |
| 玩家恢复 | 平台快照、候选玩家和原位交接 | 复用流程，新增数据模型 | 不沿用 PlatformerSnapshot 的版本、字段和地空状态恢复规则 |
| 关卡编辑 | Ember.LevelAuthoring 的 Tile、Prefab、适配接口 | 公共引擎复用，新增业务适配 | 俯视关卡描述、出生验证、试玩与相机接线 |
| 敌人与互动 | FSM 和实体能力可作为基础 | 新增最小样例 | 一个带攻击预告的追击敌人、沙袋或陷阱、可触发的互动对象 |
| 光照玩法和叙事 | GlobalLight 为场景灯光表现；Narrative 属于另一模板 | 不纳入首版 | 由产品接入；不能把灯光过渡当光区判定，或直接叠加小说模板 |

GameInputModule 与 PlayerDataModule 在读取的 base 快照中均为 `Enabled=false`，新模板必须显式启用并配置。当前平台工作副本的启用状态不代表父模板默认值。[S2]

现有 `EntityHit` 以左右符号处理击退，`PlayerHitQuery` 以方向符号镜像形状；直接复用会遗漏任意方向攻击。现有 `source3d-2p5d` 的 PlayerControl 主要控制相机锚点、拖动与缩放，也不能作为现成战斗控制器。[S3]

## 3 跨模板复用与改动归属

### 3.1 首版采用选择性移植

首版优先让 `topdown-2d` 独立形成闭环。对平台模板中已实现且适用的能力，记录来源、依赖闭包、保留契约、俯视差异和需要继承的测试，再在新模板 Assets 中适配。这里的复用包括实现与契约复用，不承诺两个平级模板自动共享一份业务源码。

不复制整套 Player 或 Entity 目录，不引用兄弟模板的快照路径，不通过让 `base` 承担所有战斗能力来实现共享。新建的俯视配置、图、Prefab 使用独立资产身份；正式迁移既有公共类型时才设计 GUID、程序集和序列化兼容策略。

选择性移植会产生后续维护成本。每次修复应依据来源清单评估另一模板是否同样受影响。若两个宿主都证明需要同一组中性运行原语，可再形成独立的公共提取批次；首版不以大规模提取为前置条件。

### 3.2 公共提取的条件

同时满足以下条件才进入公共提取：不包含 Player、平台、永夜语义；两个调用方真实使用；可明确配置与生命周期所有权；能够保留原调用方行为和资源引用。提取到包中的普通类型不因此成为 Manager，也不要求所有模板装配对应业务。

| 变化 | 长期归属 | 验证影响 |
| --- | --- | --- |
| 俯视玩家、配置、示例、工具、场景和文档 | topdown-2d 模板 | 新模板相关用例与正式启动 |
| 共享服务缺陷或确有必要的中性接口 | com.ember 或 base 的正确所属层 | 公共契约及直接受影响的既有调用方 |
| 将现有 Entity 原语正式提取为公共实现 | 框架与相关模板联合变更 | 俯视与平台两侧兼容、GUID、数据及行为回归 |
| 骑士、提灯、光区、污染、茧、烛龙、地区剧情 | 永夜项目 | 产品玩法与进度一致性 |

若没有公共缺口，首版可以主要新增模板内容。模板随 `com.ember` 交付，正式发布仍需新的框架 tag；这是交付关系，不等于必须改动公共运行 API。[S4]

## 4 模块与运行契约

以下名称表示建议职责，不是已经存在的新 API。实现时根据当前工程命名规则确定最终类型与程序集。

| 业务单元 | 责任 | 边界 |
| --- | --- | --- |
| Player | 俯视会话、输入意图、角色 Context、动作、进度捕获 | 唯一驱动玩家，不承担全部敌人和剧情规则 |
| Entity | 必要的生命、能力、效果、命中数据与角色组件 | 不依赖 Player；不是自动拥有 FSM 的全局实体管理器 |
| Combat 或战斗会话服务 | 登记参与者、收集命中、去重、稳定结算 | 每个参与者仅有一个更新所有者；不依靠各组件无序 Update |
| PlayerCamera | 绑定当前玩家、跟随与边界 | Player 不依赖 Cinemachine 类型 |
| LevelAuthoring | 俯视关卡身份、出生点、验证及正式试玩适配 | 实际地图仍以场景、Tile、Prefab 为权威 |
| Progress 业务协调 | 组合玩家与世界快照、恢复候选、保存退出 | 存储服务仅负责保存数据；恢复成功才切换活动会话 |

普通服务和组件不必各自实现一个 Module。需要独立装配或阶段生命周期的部分才成为 Module；所有 Module 显式填写 Enabled。

### 4.1 移动与输入

- 输入层输出移动、瞄准和按钮意图；不直接写角色 Transform。按钮请求跨 Update 与 FixedUpdate 锁存一次，禁止输入时清除旧请求。
- 键盘斜向输入限制在单位圆内，摇杆保留力度；速度与位移由统一物理步提交。
- 身体采用零重力二维运动；禁止携带平台跳跃的竖直重力结算、落地补次数、土狼时间等规则。
- 鼠标位置经玩法相机转换到世界平面；手柄瞄准使用死区。瞄准无有效输入时保留上次有效朝向，默认朝向可配置。
- 攻击可锁定进入时朝向，普通移动可以改变朝向；冲刺方向来源由配置声明，不在多个状态内分别猜测。
- 暂停、转场、UI 和动作对控制的限制分别持有自己的所有权，退出其中一个流程不能解除其他流程的限制。

### 4.2 状态与可扩展动作

建议最小图为 Alive 下的 Locomotion、Action、Hit，以及独立 Dead。Locomotion 内区分 Idle 和 Move；Action 承接攻击、冲刺及项目扩展动作。持续 Buff、光区、背包或剧情进度不塞进互斥动作状态。

继续使用 SO 声明与宿主持有的运行对象。每个角色独立拥有 FSM、能力资源、效果和时钟。方案在准备时捕获，运行中修改编辑资产只影响之后的新会话；不能因为资源同名就静默替换当前装配。

新增动作至少需要声明开始条件、输入与资源提交点、时长或结束条件、取消与打断规则、运动与朝向占用、动画映射、效果释放，以及是否允许保存。预检失败不能消费次数或冷却。

### 4.3 战斗与表现

- 首版制作一段近战和一种冲刺或闪避。无敌属于可配置效果，不能把“冲刺必然无敌”写成框架规则。
- 命中以攻击本地空间定义，用同一方向变换生成运行查询、刀光和编辑预览；击退为平面向量。
- 按攻击实例与窗口对实体去重，多 Hurtbox 不重复扣血。伤害、硬直、死亡和后续无敌遵循明确结算顺序。
- 首版攻击窗口采用进入时锁向；覆盖移动扫掠和短窗口跨步。任意旋转或形变的连续碰撞不在首版承诺内，后续新增须补对应验证。
- 简单敌人只需完成发现、追击、攻击预告、出手、恢复和死亡。复杂绕障、群体协作及自动行为树后置。
- 动画使用稳定动作 ID 与方向映射，缺失必要映射在准备时报告；可选回退必须显式配置。画面朝向与伤害判定不各自计算不同方向。

### 4.4 保存与世界恢复

俯视进度类型独立于 PlatformerSnapshot。首版保存场景与出生身份、平面位置、朝向、生命、能力开放/次数/CD，以及明确可恢复的效果。配置身份与数据版本必须可校验。

建议首版只允许稳定状态保存；攻击、受击、冲刺和未实现恢复协议的项目动作返回明确拒绝原因，不保存任意 FSM 叶子和 Animator 时间。普通保存同步冻结数据后异步写盘；保存退出失败应留在当前会话。

模板同时提供世界进度的组合位置，至少用一个持久互动对象证明“玩家与世界属于同一次保存”。项目负责自己的完整数据模型和对象恢复规则。死亡重试、读档、换区是不同恢复原因，不能默认全部清空世界。

恢复走读取、校验、准备候选、提交和可交互链。旧对象保留到可安全交接的阶段；提交失败后的回退或故障退出必须明确。SceneFlow 不能回滚任意业务副作用，所有可能失败的资源检查应尽量放在提交之前。[S5]

### 4.5 制作工具与目录

业务位于 `Assets/Game/Module/<职责模块>/`；UI 用户逻辑与 Binding 位于 `Assets/Game/UI/Runtime/Module/<模块>/`；配置与资源按现有类别目录组织，不建立一个混装所有内容的顶层 TopDown 文件夹。

玩家工具提供方案校验、复制、动作配置、方向预览和白盒入口，首版不照搬全部平台工具。关卡工作台复用公共编辑能力，新增俯视 `IEmberLevelAdapter` 接线；单向平台、弹射机关和平台出生检测不属于默认俯视工具。[S6]

菜单使用 `Ember/<业务分类>/<工具名>`，可沿用 `Ember/Player/玩家开发工具` 的入口约定，但当前模板只能注册一套有效实现。按 `topdown-2d` 正式身份、合法派生关系和模块启用状态控制菜单、窗口与写入操作。蓝图通过现有能力登记启用，不能因引用公共包就在所有模板显示。

## 5 分阶段实施

各阶段状态均为待实施。规模用于判断工作重心，不换算为工期；实际工作量取决于 T0 的复用审查和目标设备。

| 阶段 | 依赖与主要工作 | 阶段产物 | 退出条件 |
| --- | --- | --- | --- |
| T0 基线与复用审查 | 核对 base、现有草稿、模板创建流程；逐项审查 Entity、Player、关卡适配依赖 | 最终复用清单、目录/程序集设计、状态图、快照范围、保护与恢复清单 | 没有未归属的公共变更；选择性移植与公共提取范围明确；当前工作可恢复 |
| T1 模板骨架 | 通过项目中心创建 base 派生模板；在活动 Assets 接线输入、场景准备、玩家占位与相机 | 可走正式启动流程的空白俯视模板、模块开关、基础资源 | 新游戏、退出、重入、准备取消与失败清理可验证；base 无俯视依赖 |
| T2 移动与角色方案 | 实现向量运动、朝向、碰撞、输入缓冲、动画映射和配置捕获 | 可移动白盒、方案副本、方向标记与诊断 | 斜向、墙角、按住键恢复、暂停与多实例隔离符合契约 |
| T3 基础战斗 | 移植能力/效果/生命，适配方向命中与击退，新增近战、冲刺和敌人样例 | 可重复战斗白盒、可关闭的战斗装配 | 多方向命中、去重、短窗口、打断、受击与死亡链成立；无双重 Tick |
| T4 保存与恢复 | 接入俯视 codec、玩家快照、世界贡献、检查点和恢复策略 | 保存继续与死亡恢复流程，一个持久互动样例 | 保存/读档/重试边界明确；失败不覆盖好档、不提前破坏旧会话；世界与玩家一致 |
| T5 制作与扩展 | 完成玩家工具、关卡工作台适配、UI、身份隔离和使用说明 | 两个示例关卡、可配置角色、正式模板文档与扩展样例 | 能在不改核心运行循环的情况下新建关卡并增加一个示例动作；退出试玩恢复编辑现场 |
| T6 封存与消费验证 | 完成新增与相关验收；通过中心保存及另行授权的 Bump/发布流程交付 preview | 可追踪的模板版本、框架交付版本、验收记录和消费部署结果 | 干净消费工程部署后可跑完整链路；必要设备/构建与隔离检查有明确结果 |

T1—T3 可以在开发端逐步展示与验证，不能提前称为已交付完整模板。永夜可以并行开展需求与关卡纸面设计；正式接入以 T6 的可追踪 preview 交付为起点。

## 6 验收范围

### 6.1 自动与运行验证矩阵

| 编号 | 验证对象 | 最小可判定结果 | 阶段 |
| --- | --- | --- | --- |
| TD01 | 输入与平面运动 | 对角线无额外速度；零输入朝向稳定；暂停/转场后按住攻击不误触；模拟摇杆强度保留 | T2 |

### 6.2 人工体验与设备边界

人工检查角色是否易于控制、鼠标落点和朝向是否可读、攻击预告是否明确、UI 与玩法输入是否冲突，以及保存和恢复是否符合画面反馈。自动测试只能证明规则行为，不能签收手感。

键鼠、真实手柄、不同分辨率和 Windows Player 分开记录。模拟输入通过不等于真实手柄通过，Editor 通过不等于构建通过。移动端、主机、联网与压力极限不属于首版默认验收。

每批 C# 或程序集修改后，主动通过 Unity MCP 请求编译，确认本轮编译及域重载完成，再读 Console 并验证。全量或预计耗时较长的测试须按仓库规则取得明确授权；MCP 断连按公共规范处理，不用其他构建方式替代编译验证。[S7]

## 7 模板管理与交付

1. T0 先识别当前未保存模板内容及其他工作区改动，保留差异和可恢复基线。创建或切换模板按项目中心正式流程执行，不能覆盖现有平台与 UI 草稿。
2. 通过项目中心从实际 base 创建派生身份，所有日常修改落在活动 `Assets`。新模板的 parentVersion、父 hash 和快照由中心生成。
3. 禁止手改 `Templates~`、`ParentSnapshot~`、模板版本或 hash，也不能用脚本复制代替保存与 Bump。中心不可用时保留 Assets 和未完成状态。
4. 正常保留模板切换、Skill 同步、场景保存等确认流程；需要切换时提前说明目标与影响。模态弹窗阻塞时请用户处理，不重复提交切换或编译请求。
5. 保存、Bump、提交、框架发布、消费升级分别记录和执行相应授权。首个版本建议标记 preview；具体版本号在交付时确定。
6. 消费工程经 Ember/UPM Manager 获取对应框架版本，再通过项目中心部署模板。不得手改 manifest/lock 或 PackageCache 完成升级。
7. 交付包含版本/hash、功能范围、新增/相关验证结果、未验设备或平台、已知限制、扩展说明和恢复路径。技术失败时退回最近可用阶段；未验证批次不进入已签收版本。

## 8 提供给具体项目的接口边界

以下是需要在实现中形成并验收的能力，不预先固化未经设计的 API 名称：

- 获取只读玩家状态，发起有所有权的动作请求；项目不直接改内部 FSM 或私自 Tick。
- 提供交互意图与目标解析接入点，项目实现拾取、投放和对象交互。
- 在命中结算的明确阶段提供项目规则适配，支持光照等条件修正，不让项目订阅伤害后再补扣或回填生命。
- 接收项目的控制限制、时间暂停和相机请求，释放时只撤回自己的影响。
- 导出玩家快照片段，并由项目组合世界进度；恢复通过同一候选提交流程完成。
- 让项目定义敌人行为、死亡处理、重试与世界复位策略。

永夜不需要等模板包含其专属玩法。若项目接入时发现必须反射内部字段、复制核心循环或接管本应唯一的所有者，应判定为模板扩展点缺口，并按归属单独修正。

## 9 实施风险与决策时点

| 风险或未决项 | 处理方式 | 最迟解决阶段 |
| --- | --- | --- |
| Entity 中混有大量平台组件 | 按最小依赖闭包移植，列明排除项；公共提取另成可回退批次 | T0 |
| 当前 Assets 含其他进行中的改动 | 先保护和确认活动内容归属，不把全部工作副本当新模板来源 | T0 |
| 任意方向攻击与动画工作量扩大 | 第一版锁向攻击、简单占位方向表现；逐步补美术映射 | T2—T3 |
| 世界恢复接口过度通用化 | 用一个真实持久互动样例证明组合与事务，不先造通用对象数据库 | T4 |
| 把平台工具入口直接开放给俯视项目 | 复用编辑引擎，单独编写玩家和试玩适配；覆盖身份矩阵 | T5 |
| 复用代码在两模板逐渐分叉 | 保留来源/差异记录；在第二个真实使用场景后评估公共提取 | T0起持续 |
| 设备与性能目标不明确 | 先记录开发基线；冻结输入设备、参考机器和目标构建后再作性能结论 | T6前 |
