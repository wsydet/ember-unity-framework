### 5.2 挥旗、旗跳与风场

拟议项目动作 `FlagWave`，普通按键为旧 Act=J；模板 Attack 也使用 J，必须在 Windward 输入映射中解除冲突并关闭攻击方案。

旧事件时间来自 `Assets/Anim/temp-anim/temp-wind flag.anim` 和 `temp-air flag.anim`，片段时长 0.5 秒：

| 时间（秒） | 旧回调 | 新实现职责 |
| --- | --- | --- |
| 0.033333 | ChangeDir | 方向锁定/视觉朝向按设计明确 |
| 0.150000 | FlagStart | 进入挥旗执行段、建立强风、施加反冲、开放旗跳 |
| 0.166667 | AudioWind | 表现事件 |
| 0.216667 | FlagMid、ImpulseWind | 关闭旗跳窗口；未旗跳则Y回弹；镜头表现 |
| 0.283333 | TempFree | 释放部分运动限制 |
| 0.450000 | FlagEnd | 退出并清理动作 ownership |

逻辑窗口由动作时钟/状态定义掌握；动画事件用于表现或与逻辑同步，不能让换图后漏一个事件就永久锁死玩家。中断路径必须和自然结束一样完整清理。

规则：同一玩家仅保留一个自造风，新的替换旧的。风朝面向方向，身体反冲朝相反方向。旧美术右朝向时 scale.x=-1，不能直接把这个符号当成新框架 Facing 值。

风初始为强风；落地且非挥旗/跳跃，或弹射刷新时转为弱风并启动寿命。弱风且不在挥旗执行段，或风消失后允许再次挥旗。旗跳只在很窄窗口内接受地面跳跃，可获得额外水平速度；旧代码还要求 `rPreJumpFrames <= 2`，不是整个普通6帧缓冲都能旗跳。弹射会中断挥旗并刷新相关资格。旧帧数按60Hz解释并转换为明确时间条件，不能直接依赖新项目的固定步次数；Q05保留风场规则与数值，Q02允许基础手感适配，二者不互相替代。

`Wind.prefab` 的基础区域为宽14、高6；旧生成中心横向偏移约7.6、向上3；弱化后约90固定帧寿命（约1.5秒），不是自生成起固定1.5秒。重叠规则须显式实现：同方向强风覆盖弱风；相反方向强风抵消后是否保留弱风按旧分支还原。

以 sourceId 登记每个接触风场，进入、退出、销毁都能重算合成结果。不能复制四个 bool 的实现：多个同方向风重叠时，任一退出会错误清空仍有效的风。

源码中的16种玩家风速合成结果如下（左为负，右为正；值是用于移动基准的 windDiff，并非独立 AddForce）：

| 强风集合 \ 弱风集合 | 无 | 仅左 | 仅右 | 左右都有 |
| --- | --- | --- | --- | --- |
| 无 | 0 | -5 | +5 | 0 |
| 仅左 | -8 | -8 | -3 | -8 |
| 仅右 | +8 | +3 | +8 | +8 |
| 左右都有 | 0 | -5 | +5 | 0 |

这不是“各方向取最大值再相减”的简单公式。例如左强风+左右弱风，源码为-8，简单取最大再相减会得到-3。Q05已确认保留上述16种结果。新实现用来源集合得到四种存在事实，再应用旧规则；来源数量用于正确维护接触关系，不额外累加同类风速。玩家弱风5/强风8、载具弱风4/强风8分别配置；云沿用自己的方向选择逻辑，不共用玩家数值或强行套用玩家合成表。

实现时先登记每个来源的稳定运行期标识、方向和强弱，再在进入、退出、强弱变化、禁用与销毁时重算有效集合。相同来源重复进入应幂等；移除一个来源不能清除另一个仍有效的来源。用上述矩阵逐项回归，再验证同向重叠、反向重叠、强弱切换和场景清理。配置化的目的在于明确保留差异，不授权自动简化风场规则。

拟议FlagWave状态至少分准备、发风/旗跳窗、回弹、可操作后段、结束；优先级规则需明确“死亡/转场取消 > 弹射打断 > 当前挥旗 > 普通移动”。这是新设计建议，需在模板扩展契约上实现。造风只执行一次，任何中断都释放运动owner、输入请求、音效句柄和临时表现。不要用持续Buff替代互斥动作阶段。

4. 不调用会修改Time.timeScale的PlayerModule.Pause，不暂停场景模拟。风场寿命、平台/云移动、碎石计时、环境表现与声音继续运行，自动保存也正常执行。

### 5.6 存档与结尾

旧实现使用 PlayerPrefs JSON（bagKey/flagKey/lastKey），另有 SaveSystemB 文件实现但不能据此认定其为实际主路径。旧背包直接 JsonUtility 序列化 List 的写法有丢失内容风险（静态推断，未运行验证）；新实现不复制。

**Q03已确认：首版一个当前流程的自动存档，支持检查点续玩，保留已保存的收集与旗面进度，不导入旧存档。** 上次完成旗面单独保存为历史记录，供结尾对比，不占用第二个可选择的续玩槽。首版不提供多槽管理或任意位置手动存档。

拟议 `WindwardProgress`（项目数据类型名，可在实现时统一命名）包括schemaVersion、runId、levelId、checkpointId、稳定拾取ID集合、背包实例、已确认旗面布置、累计时间与死亡数。玩家恢复使用合法检查点基线；必要时存该基线或由检查点配置重建。关卡尚未激活检查点时使用该关入口作为初始基线。不保存当前空中位置/速度、挥旗进度、临时风场、正在移动的云或碎石剩余帧数等瞬时状态。

自动保存时机与数据一致性：

| 触发 | 保存内容与执行条件 |
| --- | --- |
| 激活检查点 | 验证稳定CheckpointId和恢复位置后，提交新检查点基线与当前已完成进度 |
| 成功拾取贴纸 | 稳定拾取ID与背包新增实例一起提交，保留现有检查点；即使人在空中，也可保存这份业务数据 |
| 确认放置贴纸 | 旗面新增布置与背包扣除一起提交；悬挂光标、未确认贴纸不写入成果 |
| 完成关卡 | 保存明确且有效的续玩目标；下一关入口就绪后才提交其levelId/入口检查点，失败不得留下不存在的目标 |
| 长按R返回菜单 / 正常退出应用 | 保存最新已完成进度、时长、死亡数与检查点基线，等待已接受写入成功后才卸载/退出；不能仅依赖应用关闭回调抢写 |

复用**base模板的** PlayerDataModule泛型codec与排队/drain；一次接受保存时冻结完整组合数据。自动保存需要追踪写入结果，只有成功落盘才算“已保存”；失败保留待保存状态并给出可重试反馈，不能先显示成功。正常退出中的保存失败不静默丢弃成果。强制结束应用只承诺恢复最近成功落盘的数据。

**区分瞬时玩家快照与进度保存。** 挥旗、弹射、死亡或旗面半放置期间不采集这些瞬时状态作为续玩快照；已经提交的拾取/旗面成果仍能与上一个合法检查点基线组合保存。未完成的放置保持在事务外，不扣除持久背包。当前PlayerModule.Save/LoadCheckpoint只认识PlatformerSnapshot，不能与另一个项目进度文件分开调用就宣称原子保存；由T05交付明确的组合保存/恢复接合点。

续玩顺序：读取并校验schema/关卡/检查点 → 加载目标关卡并复位动态机关 → 应用已拾取ID，隐藏对应收集物 → 恢复背包、旗面、统计 → 在检查点安置玩家并重置临时动作/风/支撑 → 恢复相机和输入。原子准备完成前不放开操作；无效或损坏存档明确报错，不悄悄改成新游戏。

验收示例：在森林检查点A之后，角色空中拾取一张贴纸并保存，退出再继续应回A，贴纸仍在背包且场景中不再出现；若之后已把它放到旗面并保存，续玩时保持旗面布置且背包中无该实例。机关依据复位规则重建，不能保留半途运动。续玩后重新判断出生位置所属区域：在安全区则立即停表并开放编辑，在挑战区则按Run状态计时；不沿用退出前的UI开关或区域缓存。

老DataCounter随持久对象累计Time.deltaTime。新项目按Q06使用显式RunTimer状态和区域归属控制，具体见5.7；结尾展示和保存使用最终通关判定时冻结的同一份统计，不等结尾动画播放完才停表。

## 8. 实现时必须保持的约束

- PlayerModule 是玩家唯一 Update/FixedUpdate 驱动；产品组件提供请求与数据，不另开一套物理控制。
- GameSceneScope 明确挂载参与者。跟随相机适配器在持久scope侧，Camera参与者先于Player，遵守现有提交后绑定协议。
- 模板 Scheme 在一轮会话开始时冻结；编辑新的Scheme不会自动替换当前会话；测试需重开会话。
- Player恢复不代表世界恢复。每个机关和拾取状态明确选择复位策略。
- 关闭攻击不等于关闭死亡能力。根据T04配置危险区域与生命策略，Mountain可以不显示战斗HP，但危险区仍须走唯一死亡事务。
- Q04已确定进入安全区域即开放编辑并暂停通关计时，离开后按Run状态恢复；世界继续运行。区域权限、RunTimer停表和实际编辑时的玩家局部锁分别控制，不能调用会修改Time.timeScale的PlayerModule.Pause，也不能用UI开关直接决定是否计时。
- Q06已确定挑战区游玩及死亡复活计时，菜单/暂停/设置、加载转场和结尾排除；跨关累计、最终通关时冻结。保存回菜单保留本轮，“重新开始”才清本轮，二者不得共用无差别清档逻辑；保存失败不能先卸载现场。
- Q08重新切片只处理动画资源及绑定，不以换图为由修改碰撞体、动作时长或Q05数值；额外风场声静音是已接受差异，不能连带禁用已有挥旗声、其他音效或风场玩法。
- 资源、动画与业务数据不反向依赖框架；通用补丁回模板维护源，项目不改PackageCache。
- 真实存在的API先查源码；本文拟议名不能直接当已存在接口调用。
