# 新项目实施：部署模板并实现《有趣的色彩顺序》

本阶段在新的消费项目执行。先读 [产品规则](01-product-rules.md)，再读本文；玩法数值以产品规则为准。下面的新类型与配置名均为拟新增设计，不是框架已经存在的接口。

## 1. 开工输入和完成边界

必须取得 [交接单](04-acceptance-handoff.md) 中实际交付的模板、框架版本和安装来源。`ui-game` 是候选模板 ID，`ColorOrder` 是产品技术代号，按最终交接确认。旧框架 `0.21.4` 不包含本次尚未创建的 UI 模板。

若阶段一只完成 Assets 或普通保存，缺少可安装包，先补齐对应交付；不要在新项目手工拼出模板目录或绕过中心注册。项目根目录与 Unity 工程名称由新对话上下文或用户给定，不能默认把游戏建进框架维护仓库。

本阶段默认先完成 B0 三短关及证据。B1 九关、B2 巡游按用户授权范围继续，产品试玩结论不明确时先呈现已可玩的结果与具体观察，不凭自动测试宣称好玩。

## 2. 安装和首次部署

1. **创建/核对新 Unity 工程。** 使用交接实际验证的 Unity/渲染管线组合。当前框架开发工程为 `6000.5.4f1`，这只是参考；包的最低 Unity 声明不是所有版本的验收承诺。
2. **安装真实交付包。** 首次安装按交接 Git URL/tag 和随包 README，通过 Unity Package Manager 等正式入口完成。按实际依赖声明合并 registry/依赖，不覆盖整个 manifest。Odin、DOTween 等授权及访问条件必须真实可用；UniTask 已随包内置时不再重复导入。已有工程升级走 `Ember/UPM Manager`。
3. **确认公共规则与 Unity MCP。** 查清实际解析的 Ember 包路径，读其中维护规则；可能位于 `Library/PackageCache`，仅读取。新项目根规则的同步结果、Unity MCP 的目标实例与连接都要核对，不能误操作框架工程。
4. **首次部署。** `Ember/项目中心 → 项目初始化`，选择交接的 UI 游戏模板并执行一键部署。正式派生模板已经包含父内容，不需要先部署 base 再叠加。非空项目先保护五个受管目录与既有业务，检查覆盖预览。
5. **验证初始化。** 核对活动部署身份、场景注册与映射、Build Settings、字体、EUI 页面定义、输入 EventSystem 和运行资源。屏幕方向、产品名、平台与 Player Settings 不随模板五目录自动交付，必须在新项目设置。
6. **先运行中性 Demo。** 从 FrameworkScene 冷启动，通过主页→玩法→暂停→结果→重试→主页。若失败，先定位安装/模板问题，不把未验证模板和产品代码同时堆入。
7. **建立可恢复基线。** 保存新工程初始状态、`Assets/Editor/EmberDeployedTemplates.json` 与 `ProjectSettings/EmberTemplateBaseline~/`。二者应随项目版本管理；提交按用户授权执行。

安装检查完成不等于产品完成。后续包升级不会自动更新已部署 Assets；出现通用问题按实际包内改动分流规则回到框架源或模板源修复，不改 PackageCache。

## 3. 业务组织和模板接入

建议首版一个 `ColorOrderModule`（Gameplay）统筹规则模型、配置、会话与表现协调；内部拆普通 C# 类型，不把每种机关都做成独立全局模块。产品长期进度沿用全局 PlayerData 模块，偏好沿用已有偏好模块。

```text
Assets/Game/Module/ColorOrder/
  ColorOrderModule.cs            # Gameplay 生命周期与依赖接入
  Domain/                       # 纯规则、棋盘、目标、评分、机关
  Session/                      # 局/段状态与输入事务、取消及暂停
  Content/                      # 配置模型、加载与校验
  Persistence/                  # 产品进度 DTO、codec、资格与迁移
  Editor/                       # 仅有实际制作需求时增加，独立 Editor 程序集
  Tests/                        # 本次新增/相关测试，EditMode 与 PlayMode 隔离
Assets/Game/UI/Runtime/Module/ColorOrder/   # EUI 中心实际生成路径
Assets/GameResource/Resources/UI/Module/ColorOrder/Prefabs/
Assets/GameResource/Resources/UI/Module/ColorOrder/Atlas/
Assets/GameResource/Resources/Config/ColorOrder/
Assets/GameResource/Resources/Audio/ColorOrder/
Docs/ColorOrder/                 # 产品规则、配置清单、测试及交接
```

目录按需建立，不预建空的未来系统。产品类型命名可调整，但必须同步真实生成结果和文档。Editor 不引用进运行程序集，测试不混入发行程序集；框架不能反向引用产品类。

阶段一应提供模板 Demo 的替换入口和所有权说明。优先用该接入点选择产品玩法；若交接没有可用扩展点，先补齐模板说明或最小接线，不能靠两个 Gameplay Module 同时创建页面来“覆盖”Demo。产品正式入口启用后，关闭或替换 Demo 的装配，验证它不再启动、计时或订阅输入。

`[EmberModule(ModulePhase.Gameplay, Enabled = true)]` 须显式声明；Main 阶段模块不是默认自动接线对象。入口/选关可由已有 MainState 及其页面使用已准备的数据，不为获取实例而新增产品 Manager。

## 4. 先把纯规则做出来

建议类型边界：

| 拟新增类型 | 责任 | 不能承担 |
| --- | --- | --- |
| `ColorOrderLevelDefinition` | 关卡/段/目标/步后机关/星/种子及版本配置 | 当前运行分数与已收集状态 |
| `ColorOrderBoard` | tileId 与格位映射、真实色、标签、污染层 | 从 UI 颜色反读答案 |
| `ColorOrderRuleEvaluator` | 从目标显示字段推导合法值，返回合法 tile 集合 | 播音效、写存档、移动 Transform |
| `ColorOrderMechanics` | 给定点击前状态与预告，计算确定的新棋盘 | 点击后抽取隐藏随机或直接改视图 |
| `ColorOrderRun` | runId、段/步、容错、能力、账本、成绩资格 | 全局静态共享局状态 |
| `ColorOrderSession` | 事务门控、暂停、生命周期与表现等待 | 在迟到动画回调中重新结算规则 |
| `ColorOrderProgressCodec` | DTO 序列化、版本验证和明确迁移 | 把未知数据当空档覆盖 |

配置每段带 `steps.Count - 1` 个步后效果槽，允许 `None`。每次正确非末步消耗当前槽；定格跳过也消耗槽。机关方向/交换格已体现在本步计划中，不根据实际动画次数推算。

规则操作返回不可变或独立的结果快照，例如正确/错误、得分变化、收星、旧/新格位、是否终局；UI 按结果表现。存储模型使用稳定 ID/数值/枚举，不保存 MonoBehaviour、Transform、运行时页面或动画句柄。

先做可枚举的手工关卡，不先做随机题目引擎。校验至少涵盖：颜色与标签排列、目标选项合法且数量 1/2、相邻集合约束、效果槽数、奖励格、段内分支限制、所有合法分支能通关、完整关卡全星可达。

## 5. B0 三个可直接搭建的原型夹具

以下是本包补充的原型数据，尚未经过真人试玩；它们用于开始制作和验证，不是完整正式九关。每段重置棋盘及机关方向，局内容错和定格跨段共享。所有目标字义与字体色一致，棋盘标签等于真实色；读法按下表切换。步骤 ID、奖励 ID 用 `pXX.sXX.stepXX/starXX` 等稳定命名。

### 共同棋盘

```text
九色 N9                       四色 N4
1 红  2 橙  3 黄               1 红  2 蓝  3 空
4 绿  5 青  6 蓝               4 黄  5 绿  6 空
7 紫  8 白  9 黑               7 空  8 空  9 空
```

### P01 连续点对

| 段 | 初始盘 | 读法 | 目标 | 效果槽 | 奖励星 |
| --- | --- | --- | --- | --- | --- |
| A | N4 | 文字 | 红→蓝→黄 | None、None | 无 |
| B | N4 | 颜色 | 绿→黄→蓝→红 | None、None、None | 无 |

容错 3，定格 0。每个首次正确步骤点亮路灯的一部分；出错不把已亮部分熄灭。全完美分数 7×100+2×200=1100。此夹具验证基础判定、保留错误前进度、连击、段间切换和结果页。

### P02 两种走法

| 段 | 初始盘 | 读法 | 目标 | 效果槽 | 奖励星 |
| --- | --- | --- | --- | --- | --- |
| A | N9 | 文字 | [红 或 橙]→绿 | 局部水平翻转 | 格 5，p02.a.star |
| B | N9 | 颜色 | [黄 或 橙]→蓝 | 局部水平翻转 | 格 5，p02.b.star |

容错 3，定格 0。A 选红：绿从 4→5，下一步拿星；选橙：绿 4→6，不拿星。B 选黄：蓝 6→5，拿星；选橙：蓝 6→4，不拿星。两种选择均能通关；最终一步不再翻转。两颗星全收且无误时 4×100+2×100+2×200=1000。

两段都只有两步是原型例外，用于突出选择后果。完成后用简单位置示意解释实际路径，不能强迫用户再看一长段教学。扩为正式内容时再加入 3～5 步上下文。

### P03 把一次定格用在哪

| 段 | 初始盘 | 读法 | 目标 | 效果槽 | 奖励星 |
| --- | --- | --- | --- | --- | --- |
| A | N9 | 文字 | 红→青→蓝 | 固定从头互换、固定从尾互换 | 无 |
| B | N9 | 颜色 | 红→青→蓝 | 局部水平翻转、局部垂直翻转 | 格 5，p03.b.star |

容错 3，全局定格 1。原型明确开放定格，不改变正式第 1～3 关隐藏能力的规则。

- A 第一步用定格可保持熟悉布局，免去追踪青色的第一次换位；不用也能通关，示例路线为红 1→青 6→蓝 4。
- B 把定格留到第一步可让青留在格 5，第二步收星；随后垂直翻转，蓝仍在格 6，完成即可。该路线为红 1（定格）→青 5→蓝 6。
- B 不用定格时：红 1→青 4→蓝 6，可通关但没有这颗星。提前在 A 用掉会失去 B 的奖励机会。

此局制造“先求轻松”与“留到保星”的两次用途，不要求两处都使用能力。全完美并收星时 6×100+100+2×200=1100。观察玩家能否说明使用时机；若只有一种毫无思考的用法，调整布局后重测，不能把规则跑通等同决策有趣。

### 独立冲突夹具

B0 也必须用自动测试和一个开发预览验证真正的字色冲突：真实红块写“蓝”，真实蓝块写“绿”，真实绿块写“红”，其他颜色标签保持不变。目标为“红”字、蓝色字体；按文字应点真实绿块，按颜色应点真实蓝块。这是判定夹具，不提前把正式第 6 关加入新手原型。

## 6. 制作正式 EUI

实现 UI 前调用 `ember-eui-build` 技能，先核对实际开发中心能力。Page、Popup、Item 的创建、绑定、生成、注册均走 EUI 中心；新产品内容使用 Business 路径，`ClassPath=Module/ColorOrder`。实际类名、字段、Prefab 路径以生成结果为准，不预写 Binding。

| 页面/Item 建议 | 必需交互 |
| --- | --- |
| 产品主页/选关 | 继续、关卡状态、设置；原型入口与正式内容身份清楚 |
| 游戏页 | 规则、当前及后续两目标、段/步进度、容错、分数、九宫格、机关预告、定格、暂停 |
| 色块 Item | 大字、真实色与角标、可选辅助图案、点击反馈；绑定 tileId 与当前会话 |
| 目标 Item | 一个或两个各自完整的显示选项、“或”、当前项标记 |
| 暂停/退出确认 | 遮住题面与棋盘；继续、重试、退出选关；设置状态与页面一致退出 |
| 结果页 | 成功/失败、分数明细、评级、奖励星、错误、有效用时；下一关/重试/练习/选关 |

已有模板共用设置能满足需求时复用，具体扩展按交接说明操作。不要直接手改父模板 Framework 模式生成文件，必要时创建 Business 页面并在产品侧替换注册。

`EUIItemFactory` 只创建/管理逻辑关联，不负责实例化和销毁 GameObject；宿主清晰持有二者。固定 9 格可直接管理九个实例，不必预先增加对象池。父子 Item 绑定不得同时触发两套自动逻辑创建。

GridLayoutGroup 可用于静态槽位；移动动画表现置于不会每帧把位置拉回的层或显式控制布局，动画结束对齐领域格位。不可用动画 Transform 位置作为下一次判定依据。

## 7. 生命周期和基础能力接线

使用模板已提供的 Main/Gameplay/Settings 流程。继续使用 GameGameplayState 时，Gameplay 场景要保留唯一启用的 GameSceneScope，纯 UI 可以用空参与者列表。

进入/退出、Push/Pop 返回的状态转换操作应检查结果状态。退出本次 Gameplay 关闭本次页面、取消会话、退订事件并销毁 Item；旧任务不能重新打开页面。再次进入建立新 runId，禁止模块复用时残留上一局账本。

暂停沿模板的业务暂停接线实现：停止有效计时、拒绝作答和定格、遮住题面，明确冻结/安全完成当前表现。设置状态自身不会自动冻结模块 Update；单独设 timeScale=0 也不足以覆盖所有异步任务。与状态栈绑定的 Popup 不能只通过遮罩点击关闭页面却留下设置状态。

首版采用 EUI/uGUI 点击。EmberInputManager 是框架必要基础设施，GameInputModule 是可选业务适配；只有实际需要快捷键/手柄时才开启并配置动作。保证唯一 EventSystem/UI Input Module，不让背景点击穿透弹窗。

音效复用 EmberAudioManager。配置 B0 优先使用可序列化的 ScriptableObject，Inspector 能够编辑并运行校验；B1 大量内容若采用表格，再启用 GameTableModule，走现有表格源→生成→ETBL 路径，不手工拼 `.bytes` 或直接在运行时读 CSV。不要为了六段原型先建设通用关卡编辑器。

## 8. 本地进度与异常

在 base 继承的 PlayerDataModule 上接入产品 DTO/codec。先在实际 PlayerDataConfig 中设置独立的 `directoryName`、与 codec 一致的 `dataTypeId` 和固定 `slotIds`，再检查实际装配是否 Enabled。等待 `WhenReady` 成功只表示服务已准备；随后显式调用 `ReadAsync<Progress>(slot, codec)`，等待其 `Completion`。仅 `ReadStatus.Loaded` 使用读取结果，`NotFound` 可创建新档；其他状态保留数据并进入错误处理，不能统一当作首次启动。

保存调用返回 `SaveOperation<SaveResult>`，等待 `Completion` 并检查 `Succeeded/Status`，不是调用后立即显示成功。`StopAsync` 不自动存档。

产品数据至少包含：

| 类别 | 字段 |
| --- | --- |
| 版本 | schema/data 版本、scoringVersion、内容版本、dataTypeId |
| 长期进度 | 各关解锁、最佳评级、合格最佳分与时间、装饰及里程碑已获得 ID |
| 当前检查点 | sourceRunId、模式、关卡/下一段、种子、辅助条件、恢复只可练习标记 |
| 尝试记录 | runId、通关与否、段/步、得分明细、错误、用时、定格使用、所选分支、练习/提示/辅助资格 |

使用独立产品 `DataTypeId`，不要沿用 `ember.base.progress` 或示例 level/coins 模型。配置清单与存档版本分离；新内容不能悄悄让旧最佳与不同规则比较。

把通关结果、最佳更新、解锁、里程碑和已结算 runId 放入同一完整进度快照保存。确认未提交的失败可保留候选快照，在服务允许时重试而不重复发奖；`SaveStatus.CommitUncertain` 表示提交未知，实际存储会进入 Faulted、保留现有文件并拒绝后续写入，必须停止自动重试。待旧文件所有权释放后，按实际存储恢复协议重新核对磁盘和已结算 runId，再决定如何处理；不能宣称此时旧档必然未变。偏好可用已有偏好设施，不能把主线所有状态散写为多个互不一致的 PlayerPrefs 键。

段边界检查点只用于中断后的练习恢复；进程重启不得把旧正式资格复活。完整局结束的历史成绩正常保留。无法解码或不支持版本时显示恢复选择，不静默覆盖原数据；实际恢复能力按存储服务核实。

正常退出采用显式收尾：最终快照先入队，再取得 `BeginDrain()` 的 ticket 并等待 `DrainAsync(ticket)`，核对 `Status`、`FailedWrites` 与 `PendingRequestIds`，再按结果决定是否退出。平台确有退出能力时最后走 `GameLauncher.Instance.Quit()`；不能等 Module OnDestroy 才开始保存。取消退出或处理确认可重试的失败后继续游戏，必须按契约 `ResumeRequests(ticket)` 恢复请求入口，不能让服务永久留在 Draining；提交未知仍走故障核对流程。不要为消除错误报告提前确认/丢弃尚未处理的失败记录。

每批代码变动后通过目标 Unity MCP 显式编译，确认本轮编译/域重载完成并读取 Console，再运行新增/相关测试。不要为“顺便确认框架”跑全量或长时间测试。详细规范与断连处理见 [验收文档](04-acceptance-handoff.md)。

## 10. 后续才需要的决定

正式平台、最低设备、分辨率基线、美术规格、最终产品名、发布账号和商业化尚未确定。先交付本地可玩结果；平台构建和发布前收敛这些选择，并对真实设备与目标构建独立验证。未做触屏、多指、后台切换或发布构建时，报告必须明确未覆盖，不能用编辑器鼠标通过替代。
